## 10. Module identity: prior art (survey of 2026-10-26)

**Status (2026-10-26): a survey and a design analysis, proposed, not landed.**
Nothing in this section is ruled, and nothing in it is built.
It answers one question Meng put on 2026-10-26: would a Haskell-style `MODULE` declaration that gives a file a fully qualified name solve the collision problem, and what does it do about paths on different operating systems?
He said he is willing to do the heavy lift of adding a keyword if it buys correctness and ease of reasoning.
Later the same day he asked that the existing `IMPORT` keep its meaning through a sensible fallback, with the new style working beside it.
Section 10.5 is therefore the default design (a fallback), 10.5b is three ways to add names on top of it, and 10.6 is the recommendation.
Revised five times on 2026-10-26.
After an adversarial review, the recommendation of 10.6 changed (a reserved library spelling now comes before option A) and R4 was narrowed.
After research on how other systems let a program name the standard library past a local file (10.2, points 4 and 6) and a measurement of the colon spelling (10.5.2), the spelling of that reserved library prefix changed from the unquoted dotted `l4.<library>` to the backticked `` `l4:<library>` ``; the unquoted dotted name stays proposed for project-derived names (option A, step 3).
After a second adversarial review (thirteen findings), the reach of step 2 was narrowed and stated (it protects an importer's own import of a library, not the libraries' imports of each other), its behaviour under a pinned `JL4_LIBRARY_PATH` was stated, and a resolution-order alternative was added to 10.6, "What would change this"; the order of the steps was not changed.
After a third review, by three independent skeptics of the bench cards that carry this survey (S1 to S22; each was re-verified before it was written, and 10.7 says which could not be reproduced as put), two recommendations changed and the rest were repairs.
R3 is recast as R3a (keep a self-import an error and make it readable, which `origin/main` has done since 2026-10-24 and which unstable would get by a port, item 54) and R3b (a self-import resolves to the library, the first draft's R3), and R3a is recommended; the wrapper pattern that R3b would serve is served by the reserved spelling of step 2.
R4 in the language server is a warning published as a diagnostic on the `IMPORT` line, because the server today logs the shadow warning to its stderr and publishes nothing.
The other findings corrected counts, citations and credits (TC39, Go, Catala), added costs (two doc pages, the browser build, `MODULE` as an identifier) and stated that only 6 of the 22 libraries are free of a project file through their own imports.
After a fourth review, an adversarial review of the fourth revision (eleven findings, each re-run or re-read before it was written), R3a is stated as a port of three commits that conflict with unstable and with #751, and not as a pick of two, and its edge rule has to be re-based on the classifier.

**What the table says** [argued from the rows].

1. Where the tool looks files up on demand, name and path agree by construction (Lean, OCaml, Python) or by a checked rule, and the checked rules have three different shapes.
   Haskell and Elm check a declared dotted name against the name derived from the file's whole path, which is the shape of option A.
   Catala compares the declared module name with the file's base name only, as `String.to_id` of each (`parser_driver.ml:523-527`), and finds modules by the lower-cased base name in one flat namespace across the include directories (`parser_driver.ml:684-690`): it is not a path-derived dotted name [src, the researcher's copy of `CatalaLang/catala@f32ea23`].
   Go has no per-file declaration: the module path is in `go.mod`, an import path is that plus the directory, and the `package` clause is a local name; a `package zzz` in a directory `bar`, imported as `example.com/m/bar` and used as `zzz.F()`, built and ran with exit 0 [ran, go 1.25.5, fourth revision].
   Go is therefore precedent for option C, a project name plus a path, and not for A.
   A name free of the path appears only where the build is handed the file list (PureScript) or a manifest lists the modules (Cabal's `exposed-modules`, Catala's `clerk.toml`, Lake's roots).
2. A declaration alone does not make a name unique across projects.
   Haskell tolerates the clash until import, PureScript errors, Elm cannot disambiguate, Catala has one flat namespace.
   Prevention comes from a project-scoped prefix: Go's module path, Rust's crate name and version, OCaml's wrapped libraries, Java's reverse-DNS convention (a convention, not enforced).
3. A local file against a library module is silent in Haskell [ran], Rust, dune (a module named like its library becomes the library's interface) and Python, and loud in Elm, Go (`ambiguous import`) and Lean (loud, but it names the wrong file).
   Python takes the local file at the import without a word; since 3.13 a later `AttributeError` carries a hint that the script has the same name as a standard library module [doc, What's New in Python 3.13, re-read in `raw/pywhatsnew313.txt`], so it is silent at the import and explained only when something fails.
   Declared names did not prevent Haskell's silence; loudness at the point of choice is what protects Elm, Go and Lean.
4. A reserved prefix answers "which side is the library": Go uses first path elements without a dot for its standard library and warns module authors off them, Java reserves `java` (javac refuses `package java.lang`), PureScript refuses `Prim…` modules [3] [9] [2].
   Lean has none: a project library rooted at `Std` took the whole root name and hid the toolchain's, with an error that names the wrong file [ran] [4].
   R-escape (entry 20) adds the spellings by which a program names the standard library past a local file, including two systems outside the twelve (Node, Deno) and a TC39 proposal that did not advance, with what each cost and what its designers said.
   - **Node, `node:`.**
     A correction first: in Node a bare core name already beats a file and an npm package.
     "Some built-in modules are always preferentially loaded if their identifier is passed to `require()`. For instance, `require('http')` will always return the built-in HTTP module, even if there is a file by that name." [doc, modules.html, "Built-in modules"]
     With `./fs.js` and `node_modules/fs/index.js` both present, `require('fs')` was the builtin and `require('./fs')` the local file [ran, node v26.4.0].
     What `node:` buys is three things.
     It bypasses the require cache: "if a name matching a built-in module is added to the cache, only node:-prefixed require calls are going to receive the built-in module" [doc, modules.html, "Caching"].
     It is an absolute-URL form: "This URL scheme allows for builtin modules to be referenced by valid absolute URL strings." [doc, esm.html, "node: imports"]
     And it is a mandatory prefix for builtins added later: "This requirement exists to prevent newly introduced built-in modules from having a conflict with user land packages that already have taken the name." [doc, modules.html, "Built-in modules with mandatory node: prefix"]
     `node:test` is "only available under the node: scheme" [doc, test.html]; `require('test')` failed with `MODULE_NOT_FOUND` beside a local `test.js` while `require('node:test')` returned a function, and an unknown `node:` name threw `ERR_UNKNOWN_BUILTIN_MODULE` [ran].
   - **Deno, `node:`, `jsr:`, `npm:`.**
     "Third party modules are typically imported from a remote registry and start with jsr: or npm:." [doc, modules page]
     Deno 2.7.12 (the local binary; the pages fetched describe 2.9): a bare `fs` with no `deno.json` failed, `error: Import "fs" not a dependency`, with the hint `If you want to use a built-in Node module, add a "node:" prefix (ex. "node:fs")`; with `{"imports":{"fs":"./fs.ts"}}` the bare `fs` reached the local file while `node:fs` in the same file still returned the Node builtin [ran].
     The 2.9 pages say a bare builtin name now works and still advise "Prefer the explicit node: form anyway: it is unambiguous", and "A deno.json imports entry or package.json dependency of the same name still wins over the built-in" [doc; 2.9 not run].
     The pages give no stated motive and do not discuss local-file shadowing.
   - **TC39 proposal-built-in-modules, `js:`.**
     "To import modules from the standard library the engine has to be able to distinguish between standard library modules and other (user defined) modules." [doc, README, "Import Semantics"]
     Its answer is a prefix, preferred because it "does not introduce new syntax for loading standard library modules", and reserved: "The `js:` prefix will be reserved as the namespace for the JavaScript language only and will be governed by TC39", with the namespace registered with IANA "to prevent collisions in the future" [doc, "Namespace"].
     It considered the dotted form and rejected it: "The downside of using `std.________` is that it start to look like a global object that is also available in other contexts." [doc, Appendix A]
     It also rejected URLs with a domain ("does not always make sense outside of a web context") and npm-style `@std/…` [doc, Appendix A].
     It is not a standard and no engine made it a choice: the proposal was presented for Stage 2 on 2020-09-24 and did not advance, and the committee's notes of that meeting (item "Builtin Modules for Stage 2") conclude "The proposal will not advance." [doc, tc39/notes `meetings/2020-09/sept-24.md`, re-fetched in the fourth revision].
     The notes record Mozilla and Google as prepared to block ("Google and Mozilla are on the record for blocking this"), and the objections quoted concern whether the JavaScript library would ever move from globals to built-in modules ("little interest from web standards bodies in migrating from globals to BIMs"; "this proposal doesn't give anything that's exposed by js:"), with Mozilla adding "I am not opposed to the building blocks" [doc, same notes].
     So the README's quotations above are accurate and show what its authors weighed, and the weight of precedent for a prefix on the library side lies with Node's `node:` and Deno's schemes, which are shipped.
   - **Rust, a leading `::`.**
     "Beginning with the 2018 Edition, paths starting with :: resolve from crates in the extern prelude." [doc, Reference, "Path qualifiers"]
     "If you have a local module or item with the same name as an external crate, a path beginning with that name will be taken to refer to the local module or item. To explicitly refer to the external crate, use the ::name form." [doc, Edition Guide]
     The local item won silently and `::foo::f()` reached the crate [ran, rustc 1.96.0, edition 2021].
     The cost its designers record is a change of meaning: "The prefix :: previously referred to either the crate root or an external crate; it now unambiguously refers to an external crate." [doc]; under `--edition 2015` the same `::foo::f()` called the local `mod foo` [ran].
     Crate names are not reserved: a local `mod std` compiled with no warning [ran].
   - **GHC, `PackageImports`.**
     `import "base" Data.List` "may be used to disambiguate an import when the same module is available from multiple packages, or is present in both the current package being built and an external package" [doc, "Package-qualified imports", Since 6.10.1].
     GHC's own note: "You probably don't need to use this feature, it was added mainly so that we can build backwards-compatible versions of packages when APIs change. It can lead to fragile dependencies in the common case: modules occasionally move from one package to another, rendering any package-qualified imports broken." [doc]
     A local `Data/List.hs` won silently under a plain `import Data.List`, and the quoted form reached the library [ran, ghc 9.10.3].
   - **Java, a qualified `java.*` name.**
     The prefix is enforced twice: `package java.lang;` was refused at compile time (`error: package exists in another module: java.base`) and `defineClass` threw `SecurityException: Prohibited package name: java.lang` [ran, javac 21.0.12.1].
     A qualified name escapes a local type's shadow: a local `class Integer` and `java.lang.Integer.valueOf(7)` in one expression gave `LOCAL Integer | 7` [ran].
     But the first segment of a dotted name can itself be obscured: "a variable will be chosen in preference to a type, and that a type will be chosen in preference to a package" [doc, JLS 6.4.2]; with `int java = 1;` in scope, `java.util.Collections.emptyList()` failed with `error: int cannot be dereferenced` [ran].
   - **OCaml, `Stdlib.`.**
     A local `list.ml` shadowed `List` silently (`List.length [1;2]` gave 999) and `Stdlib.List.length [1;2]` gave 2; a local `stdlib.ml` made the build fail with `Error: Unbound module "Stdlib"`, so the dotted root is itself a name in the user's namespace [ran, ocamlopt 5.2.1].
   - **Go: no spelling.**
     "The Go standard library uses package paths that do not contain a dot in the first path element" [doc, go.dev/ref/mod]; a local directory `./math` did not capture `import "math"`, and the local package is reached by its module path [ran, go 1.25.5].
     The reservation of dotless first elements is documentation and convention, not enforced when a module is made (the paths `example` and `test` are "reserved for users"): `go mod init math` printed no warning [ran].
   - **Python: no spelling, only launch flags.**
     `-P` and `PYTHONSAFEPATH` (3.11) and `-I` (3.4) keep the script's directory off `sys.path`; `python3 main.py` loaded a local `json.py` and `math.py`, and `python3 -P main.py` loaded the real ones [ran, Python 3.14.5].
     The tutorial says of the search path: "This means that scripts in that directory will be loaded instead of modules of the same name in the library directory. This is an error unless the replacement is intended." [doc]
5. A file importing itself is loud in Lean: "module imports itself" [4].
   L4 is loud too, and how readable it is depends on the tree: `origin/main` prints "This IMPORT names the file it is in. A file cannot import itself." on the `IMPORT` line, beside a GraphException; unstable, #748 and #751 print the GraphException alone (10.4b, "Trap 1 on `origin/main`").
6. The shapes of escape spelling, and which can be told from a path by syntax alone [argued from point 4].
   (i) A scheme-like prefix on the library side: `node:`, `jsr:`, `npm:`, and the `js:` of the TC39 proposal that did not advance.
   It is an absolute-URL form, and a file specifier is one that starts with `/`, `./` or `../` (Node's modules page: "Without a leading '/', './', or '../' to indicate a file, the module must either be a core module or is loaded from a node_modules folder"; the HTML specification's "URL-like" test) [doc], so the prefix is told from a path by its text.
   (ii) A marker on the local side, with the library as the unmarked default: Node's `./`, Dhall's `./`, `/` and `~/`, where a bare word is a variable and never a file (`printf 'Prelude' | dhall` gave `Unbound variable: Prelude` beside a local file `Prelude`; `./Prelude` loaded it) [doc] [ran, dhall 1.42.3].
   (iii) A leading token that is not a name: Rust's `::`, GHC's quoted package string (`import "base" …`).
   (iv) A dotted root: `java.`, `Stdlib.`.
   It is the one shape whose first segment a name in scope can capture (Java's `int java`, OCaml's `stdlib.ml`), and the one that the `js:` proposal's README weighed and rejected as `std.X`.
   (v) No spelling, only resolution order or a launch flag: Go (a dotless first element is the library), Python (`-P`, `-I`), Deno 2.7.12 (a bare builtin is an error with a hint).
   No system in this research uses a `/`-qualified spelling as the escape: every one that tells a file path from a name does it with a scheme, a marker on the local side, or a token that is not a path, which fits L4's constraint that `l4/math` cannot be told from a relative path.
   Go is the exception in kind: it rejects relative import paths in module mode, so it never has to tell a file from a name [ran, go 1.25.5], and it separates the library from other module paths by a lexical rule on the first element, which is shape (v).
   L4's present behaviour is its own case: the local file comes first, announced by a warning at the import in the CLI (the language server writes the same text to its stderr log and publishes no diagnostic, 10.5.3 R4) and not announced in the service response, in WASM or in pinned runs (10.4b, 10.5.4), and no spelling reaches the library [argued from 10.4b and 10.5.4].
   Python is the nearest: the local file also comes first and there is no spelling, but its protection is a launch flag (3.11) and a hint when something fails later (3.13), where L4's CLI warns at the import itself [ran for Python; measured for L4, 10.4b].
   GHC, Rust and OCaml pair a silent local-first order with a spelling that reaches the library [ran].
   The other half is resolution order: Node sends a bare core name to the library and needs a marker for a file, and Go sends a path whose first element has no dot to the library.
   L4 has the marker already (`./prelude`, T2b); the order is the part it lacks, and 10.6 ("What would change this") weighs it [argued].

**What every system does about portability.**
Most do nothing, and say so by saying nothing: the documentation of Haskell and GHC, Elm, Dhall, OCaml, Catala and Nix has no sentence on case, normalisation or reserved names.
The ones that act are few.
Go rejects reserved Windows names in module paths on every OS and keeps module paths ASCII; Lean rejects reserved names in a module name (with gaps); Cabal and cargo warn; Python and Java refuse a wrong-case name at lookup, so macOS behaves like Linux; dune accepts ASCII only.
Most of the rest accept a wrong-case name on a case-insensitive disk (Haskell, Elm, Lean, Rust, Dhall, a lone Go import) and fail on Linux, which is the silent form.
Nobody normalises a module name: Haskell compares strings, Elm and Lean fail in ways that print two identical-looking names, and Python normalises identifiers in the lexer while its finder compares raw bytes.
The systems that avoid the whole class restrict names to ASCII (Go, dune, Nix path literals, Rust for file-backed modules).
A dotted logical name has no separators at all, but every system that maps it to a path (Haskell, Elm, Lean) takes the file system's rules back at the lookup; the Haskell, Elm and Lean rows above are the evidence.

**Consequences for L4** [argued from the rows].
(a) A static, OS-independent rule on names (Go's, Lean's, Cabal's shape) fires on every machine, so a Windows problem is found on a Mac; Lean's gaps (`NUL.txt`, `:`, a trailing `.`) show the list has to be Microsoft's whole list, with extensions.
(b) Checking case at lookup (Python, Java) turns the silent wrong-case acceptance into an error everywhere.
(c) Comparing a declared name with a name derived from a directory listing needs both sides in one normalisation form, because HFS+ returns NFD; GHC and Elm both print the identical-looking mismatch for this.
(d) A zip entry name is whatever bytes the zipper wrote, so an identity derived from entry names inherits that; a name written inside the file does not.
(e) A relative path has no `file:` URI form, and a relative path put after `//` makes its first segment the host: this is the grammar behind the first-path-segment failure of 10.4 [measured in Python; L4's use of it is in 10.4].

**File-name hygiene of the existing corpus** [measured by this section's author, 2026-10-26]: Windows-reserved names, non-NFC names and case-fold clashes among `.l4` paths, in `legalese/commons` `origin/main` (3,973 files) and in [W] (1,505 tracked files): none of the three in either tree; one non-ASCII `.l4` path in [W], the Hebrew fixture `jl4/tests-cli/fixtures/relative-import/hebrew/חוק.l4`, and none in commons.

**Verdict on the accent and Hebrew folder failure** (the question was whether NFC against NFD explains it).
[measured] It does not.

### 10.5 The default design: a backward-compatible fallback

Meng, 2026-10-26, verbatim: "Engineering backward compatibility with the existing corpus would be preferable of course but if we need to do a refactor and mass edit we can do that if we have to. Now better than later."
And: "Can't the existing IMPORT behaviour preserve its existing semantics through a sensible fallback? And the new-style usage could also work."
The default design is therefore a fallback with four requirements, and every MODULE option in 10.5b has to meet them (requirement (1) is a stated preference and not a hard constraint: Meng wrote "preferable", and allowed a refactor and a mass edit "if we have to"):
(1) a bare `IMPORT` keeps today's resolution order for files that do not opt in;
(2) the new form is told apart from Stage 1's path form (a backticked name containing a slash) by syntax;
(3) two spellings that reach one file are one module (canonicalised by file identity), and a file with no `MODULE` line has a name derived from its path;
(4) bare-name behaviour changes only where today's answer is a crash or silently wrong: (a) a file's import of its own name is no longer an unreadable crash alone: it is also an error, on the `IMPORT` line, that says what is wrong (R3a, recommended, which `origin/main` already has and which unstable would get by a port and not a pick, 10.5.3) or, as the alternative, it reaches the library (R3b), (b) a bare name that matches both a local file and a library is a warning or an error, announced wherever the check can reach (R4).
Under R4, requirement (4b) would be met in the CLI (a stderr warning) and in the language server and the editor (a published warning diagnostic), and is unmet in the service response, in WASM and in pinned runs (10.5.3 R4, 10.5.4); today the language server only logs the warning to its stderr.
Requirement (1) is also what excludes a different fix, giving the 22 library names priority over local files (order E); 10.6 ("What would change this") weighs it.
Order E is not merely the relaxation of a ruled order.
The earlier library-resolution spec, `specs/todo/LIBRARY-RESOLUTION-SHADOW-SPEC.md`, offered Option B (embedded wins) and Option B-prime (project-scoped copies above the embedded copy, "RECOMMENDED core"), and said "Leave the B-vs-B′ call to Meng" [read].
B-prime was built (commit `ceaa23aaa` of 2026-07-19, "embedded stdlib outranks ambient XDG/bundle copies (B′) + shadow warning", carried into unstable by #134) and is the rule that `doc/reference/libraries/resolution.md` states ("Project-scoped beats embedded ... a conscious, visible act") and that `jl4-service/src/Compiler.hs:40-47` describes for bundles [read].
No recorded ruling of B-prime was found in `specs/` or `doc/`, the only places this revision searched (not the rulings sheets or the memory notes) [read].
So order E takes Option B's side of the question the earlier spec reserved to Meng, in a narrower form (22 names, and a marker for the local file), and the exclusion by requirement (1) is a ruling still to be made and not an oversight.
Everything below is proposed, not landed.

#### 10.5.1 Does Stage 1's slash rule already meet (1) and (2)?

Yes for paths, with four corrections to how it was put to Meng (R-migration §4; probes p1 to p16).

- (1) holds.
  The resolver files on `unstable` are the same as at Stage 1's merge-base (`git diff 977691b36 origin/unstable` over `Rules.hs`, `Resolution.hs`, `Shake.hs`, `Oneshot.hs` is empty), so Stage 1's diff against its merge-base is its diff against unstable [measured].
  The branch point is `writtenImportName` [W:jl4-lsp/src/LSP/L4/Rules.hs:944-949]: a bare name is `takeBaseName` of what was written, as before.
  The only addition for bare names is the warning of §4.2(3), which fires on 0 of the 953 corpus `IMPORT` lines (none has a dot or a suffix) [measured].
- (2) holds for the path form, by text alone: `classifyImport` [W:jl4-core/src/L4/Import/Resolution.hs:162-167] tests for `/`, and a slash can be written only inside backticks, so a path cannot be mistaken for an identifier.
  A backslash is an ordinary character [read].
- Correction 1: on the Stage 3 branch the rule is four-way (bare, relative path, leading slash, `@alias/…`), and the `@` clause is tested first, so a relative path through a folder whose name begins with `@` must be written `./@folder/mod` (spec §4.7 C6a; no corpus file is affected).
- Correction 2: for a name with a slash the meaning changes from unstable, where it was silently reduced to its basename; that is the point of Stage 1, and it reaches 0 of 953 lines [measured].
- Correction 3: the dotted spelling is not free.
  An unquoted dotted name is cut at the last dot, so `IMPORT a.b` is module `a`, `IMPORT Legalese.Commons.Penal` is module `Legalese.Commons` (not `Legalese`), `IMPORT l4.prelude` is module `l4` [measured, p2, p4, p1, p5].
  "Reduced to `a`" is exact for two segments only.
  This holds where the import is resolved by the language server's rules, which is the CLI, the language server and the service [W:Rules.hs:944-949, `writtenImportName`] [read]; the service's `` IMPORT `./lib/math` `` row on unstable (10.4b, T2c) shows the same reduction [measured].
  The pure resolver of WASM and the browser does not cut: `extractImportNames` returns the written text unchanged and `vfsLookup` tries it as the key, with and without `.l4` [W:jl4-core/src/L4/Import/Resolution.hs:245-250; U:jl4-core/src/L4/API/VirtualFS.hs:74-79] [read, and R-migration §5.2], so there `IMPORT a.b` looks up the key `a.b`.
  A rule that changes what a dotted name means has to change both resolvers.
  The colon spelling does not have this cost: a backticked `l4:prelude` has no dot, so the cut leaves it whole; today it is looked up as a file called `l4:prelude.l4` and not found (P1), and so is `l4:actus-core` (P2) [measured, R-colon].
  The cost therefore bears on the dotted spelling for project-derived names (step 3 of 10.6) and no longer on the spelling of the reserved library prefix (step 2).
- Correction 4: (2) as worded asks only that the new form differ from the path form.
  A new slash-free form must also differ from the bare form that Stage 1 keeps cutting, and Stage 1's rule does nothing for that.
  For the unquoted dotted form the difference lies in the parser's name (10.5.2), which a classifier that sees only text cannot see.
  For the reserved colon form it lies in the text: a backticked slash-free name that starts with `l4:` is told from a bare name by its prefix, as the slash rule tells a path from a bare name, so `classifyImport` can do it, provided the test runs before the guard that calls every slash-free name bare [read, W:jl4-core/src/L4/Import/Resolution.hs:162-167].

**The lookalike, weighed** [doc, measured and argued as tagged].
RFC 8089 Appendix E.2 defines a drive letter as one letter (`drive-letter = ALPHA ":"`), and E.2.1 warns that a relative reference starting with a drive letter would be read by a generic URI parser as a URI whose scheme is the drive letter [doc, 10.1 (7); the table cites [17]].
`l4:` is two characters, so it is not a drive letter.
The one-letter case is the dangerous one, and a function was run on it: `System.FilePath.Windows.takeBaseName` cuts `c:prelude` to `prelude` and leaves `l4:prelude` whole [measured, R-colon §3].
`Rules.hs` imports `System.FilePath` unqualified [W:jl4-lsp/src/LSP/L4/Rules.hs:40] and `main-tag.yml` builds `l4` for Windows [W:.github/workflows/main-tag.yml:116-118], so on that build `` `c:prelude` `` would be read as the library `prelude`, with a warning that undoes the spelling, and `` `l4:prelude` `` would not [argued; not run on Windows].
So a reserved prefix must not be one letter.
Spec §4.7 C6a lists `vn10:nouns` as an alternative for aliases and names the same lookalike as its cost ("a colon is also a Windows drive letter and a URL scheme, which a reader may take it for"); Stage 3 built `@alias/path` instead, and C6a is proposed, not ruled.
The one-letter argument above answers that cost for `l4:`, and it would answer it for an alias of two or more letters; it does not answer it for a one-letter alias, where the prefix is not fixed.
The two rulings are linked: a colon spelling for aliases and a colon spelling for the reserved library prefix stand or fall on the same lookalike objection, so the ruling on C6a and the ruling on the spelling of step 2 should be taken together.
A colon is not a legal character in a Windows file name, since it introduces an NTFS stream [argued], which is a second reason for the reserved form never to be probed as a file name: R1 probes the library's name with the prefix removed.

Chosen (proposed), in two parts.
**For the reserved library prefix (step 2 of 10.6): the backticked scheme-like `` `l4:<library>` ``**, written ``IMPORT `l4:prelude` ``.
**For names derived from project paths (option A, step 3 of 10.6): the unquoted dotted name**, distinguished by the parser's name.
The evidence changed the choice for the library prefix from the first draft, which chose the unquoted dotted `l4.<library>` and rejected the colon spelling as a drive-letter and URI-scheme lookalike without weighing the precedent.
Why it changed:

- _Precedent._ Node and Deno ship a scheme-like prefix for builtins (Node's stated reasons are a cache bypass, an absolute-URL form and a mandatory prefix for builtins added later; Deno's pages state none), and in Node a bare core name already beats a local file (10.2, point 4).
  The TC39 `js:` proposal stated the purpose of telling standard modules from user modules, preferred a scheme-like prefix because it "does not introduce new syntax", and weighed `std.X` and rejected it as looking like "a global object"; but it did not advance (presented for Stage 2 on 2020-09-24: "The proposal will not advance."), so it is a reasoned proposal and not a choice any engine made.
  The one enforced dotted root, Java's `java.`, still has its first segment obscured by a variable in scope, and OCaml's `Stdlib.` is broken by a local `stdlib.ml`.
- _No built form that the corpus uses changes meaning._ A backticked `l4:` name is not found today, unless a file literally named `l4:<name>.l4` sits beside the importer (X1); the corpus holds no colon path (0 of 1,505 and of 3,973), so nothing that resolves in the corpus is reinterpreted, and a project outside it that holds such a file would see its import mean the library instead [measured, argued].
  The ruling that the dotted form needs (below) is not needed for libraries.
- _No parser, printer or lexer work._ The lexer takes backticked text as written, the exact printer reproduces the line, `prettyLayout` should re-quote it [read], `l4 batch`, which re-prints a module with it and re-runs the result, exited 0 on a colon import (the printed text itself was not captured), and the classifier tests the text (10.5.1, Correction 4; the Migration paragraph and "Implementation cost" of 10.5b say what was run).
- _Hyphens are natural._ Ten of the 22 libraries have a hyphen (`actus-core`, `actus-daycount`, `actus-events`, `actus-schedule`, `actus-state`, `actus-terms`, `date-compat`, `excel-date`, `legal-persons`, `negation-as-failure`); `` `l4:actus-core` `` needs nothing special (P2), where the dotted spelling needed the mixed form ``l4.`actus-core` ``, which parses and is cut to `l4` on today's binary (q1), because an unquoted `l4.actus-core` does not lex (a hyphen is an operator).
- _Room to grow._ New standard-library modules could later be offered under the prefix only, as `node:test` is, so that they cannot collide with a project that already owns the name; that is a later ruling and no part of this recommendation.

The reasons for the unquoted dotted name for project-derived names are these.
It is what seven of the twelve surveyed systems write (Haskell, PureScript, Elm, Lean, Java, Python, and OCaml with `qualified` subdirectories); Catala is not among them, because its `> Using` takes one name and its dotted `Bar.Fizz` qualifies an item inside a module, not a module [doc, the Catala book, `book-print.txt` lines 9803-9810].
It also mirrors a `MODULE Legalese.Commons.Penal` declaration, which parses with the same `name` parser, and it needs no new token at the use site; its cost is the one named below.
It is the one spelling in the table that changes what an already-built form means: unquoted `IMPORT a.b` and `IMPORT Legalese.Commons.Penal`, which the CLI, the language server and the service cut today (the pure resolver already looks the dotted text up as a key, 10.5.1).
So it needs a ruling, and the ruling falls due before step 3 and not before step 2; two things bound it.
Unstable and commons have none: no `IMPORT` line of the 953 (and none of the 12,396 in `legalese/commons`) contains a dot [measured, R-migration; the unquoted dotted lines were counted again in the fourth revision, 0 on unstable at `63254397f` and 0 in commons at `996b8a55b`].
The Stage 3 branch has two, both #748's own test fixtures: `jl4/tests-cli/fixtures/relative-import/shortened/dotted.l4:1` is `IMPORT a.b`, which step 3 would flip from module `a` to a qualified name, and `ext.l4:1` is `IMPORT foo.l4`, which keeps its meaning (R1 below) [measured, `git grep` over `*.l4` in [W]].
Outside those, the only dotted names that exist at all use the `.l4` suffix: 12 files in `sandbox2/aswathy` and one service test string (spec §0 #16), and those keep today's meaning (R1 below).
That is a measurement of emptiness on two trees, not a syntactic guarantee.
What the syntax does guarantee, under R1 (qualified names) and R2, is that the meaning of an unquoted dotted name no longer depends on which files exist.
If Meng prefers not to change a built form at all, the syntax-distinct alternative for project names that changes no built form is `IMPORT MODULE X.Y`; its cost is a second keyword form.

Two costs the dotted spelling carries for project names, and the section does not resolve them.
The first is the `js:` proposal's objection to `std.X` seen from the other side: a dotted name starts to "look like a global object" (10.2, point 4); the proposal did not advance, so this is an argument and not a decision.
The colon spelling avoids it for library names; for project names it is stated again here.
The second is the collision with section qualification.
An unquoted dotted name already has a meaning inside L4 code: the `QualifiedName` shape that the parser builds for it is the shape of section-qualified references (`` `Section A`.sharedValue ``) and projection chains [W:Print.hs:433-439; W:Syntax.hs:34-36; W:TypeCheck.hs:4307, 4745-4795] [read].
So a later module-qualified reference to an imported name (Haskell's `M.f`, Catala's `Bar.Fizz`) would collide with section qualification and would need its own rule to tell a module from a section.
This section proposes no such reference: R1 to R5 change only how an `IMPORT` finds its file.
The question is deferred, not ruled out.
A `MODULE` line is not needed to refer to an imported symbol qualified.
After `IMPORT math`, `#EVAL Math.Constants.EULER` gives 2.718281828459045 through the section path of the imported name [ran, Stage 3 binary, fourth revision].
`specs/todo/MODULE-BOUNDARY-SPEC.md` §2.1 measured the same on 2026-09-05 ("Cross-module qualified access already works. It was never missing."), its R1 and R2 (§4) are built, and Meng's question there was "a fully-qualified way of referring to specific symbols, isn't that scope?" (§1, ruling D8).

#### 10.5.3 The rules (proposed, not landed)

- **R1, classification.** Two kinds of written name are new, the library reference (step 2) and the qualified name (step 3); every other name is classified as built.
  _The reserved library prefix (step 2 of 10.6)._
  A backticked name that starts with `l4:` and contains no slash is a **library reference**.
  It is looked up in the **library tiers** only, by the part after the colon taken whole (not cut at a dot, no `.l4` stripped: this section's choice, so that `` `l4:prelude.l4` `` is an unknown library and not `prelude`), and never in the project's tiers [proposed, assumed, not ruled; argued, not built].
  The library tiers are this section's partition of the ladder listed in the comment at [W:Rules.hs:441-449]: `$JL4_LIBRARY_PATH` when it is set, otherwise the embedded copy, then the XDG data directory and the VS Code bundle.
  The comment draws the line elsewhere: it counts `$JL4_LIBRARY_PATH` with the project root and the importer-relative directory among the project-scoped tiers 1 to 3 [W:Rules.hs:451-453], and it calls the variable an operator override.
  This section puts it with the libraries because the variable names a store of libraries, which is what a pinned run points at (CLAUDE.md §3.1) [argued].
  The project root, the importer-relative directory and the virtual-file tier that `resolveImportQuietly` probes first (the `project:/` buffer, and the importer-relative and root-relative files) are skipped.
  The ladder's own rule is kept, that with `JL4_LIBRARY_PATH` set the embedded copy is not consulted, because the operator has taken control of the library store [W:Rules.hs:458-459, 500] [read].
  So under a pin ``IMPORT `l4:prelude` `` reads the pinned directory's `prelude.l4`, and setting `JL4_LIBRARY_PATH`, which is the advice of the shadow warning [W:Rules.hs:925-928], takes effect on `l4:` imports as it does on bare ones.
  In the service and in WASM the only library tier is the embedded copy (`EmbeddedStdlibOnly`, [W:jl4-service/src/Backend/Jl4.hs:158]; the pure resolver) [read].
  The variant "the embedded copy alone, whatever the pin" is not recommended [argued].
  The golden suite and CI pin `JL4_LIBRARY_PATH` at the tree's libraries (CLAUDE.md §3.1), so a rewritten file would be checked there against the binary's embedded copy and not against the tree under test; in one pinned program bare `prelude` (a file URI) and `l4:prelude` (`jl4-embedded:`) would be two modules, against R5; and setting `JL4_LIBRARY_PATH` would have no effect on `l4:` imports.
  Why never the project's tiers: a local file that can stand in for the library is the trap itself.
  The probe is for `<library>.l4` in a library directory, with the prefix already removed, so no file named with a colon is ever probed, and a colon is not a legal character in a Windows file name (10.5.2).
  The test runs on the written text and before the guard that calls every slash-free name bare; a name with a slash stays a path import, as today's binary reads it (P8: `` `l4:sub/prelude` `` is a path to a folder called `l4:sub`).
  R-colon's item 6 would instead run the prefix test before the slash test, so that `` `l4:sub/prelude` `` is not read as a path to a folder `l4:sub`; which of the two is better is open [proposed, assumed, not ruled].
  The prefix is lower case: `L4:prelude` stays a bare name (P4), and whether a hint is worth giving is open.
  It is a new `ImportForm` constructor and not a `BareImport` whose prefix is stripped: a stripped `BareImport` would make `GetImports` see that the written text differs from the module found and emit `shortenedImportWarning`, whose advice is to write `IMPORT prelude`, undoing the spelling [read, W:Rules.hs:1617-1625].
  It applies in every resolver that shares `classifyImport` (the CLI, the REPL, MLIR and the language server through `Rules.hs`, and the service through `jl4RulesIn EmbeddedStdlibOnly`, which resolves every import [W:jl4-service/src/Backend/Jl4.hs:158; W:jl4-lsp/src/LSP/L4/Oneshot.hs:106], and through `unresolvedImports`, which calls `writtenImportName` and feeds the WARN log) and, with a prefix strip of its own, in the pure resolver of WASM and the browser, which on unstable does not share the classifier: `apiModuleLookup` looks the written text up as a key and never reaches `classifyImport` ([U:jl4-core/src/L4/API/VirtualFS.hs:99-101]; 10.5b, "Implementation cost") [read, R-colon §4].
  Open PR #752 (stacked on #748, not on #751) rewrites that resolver so that it classifies, because `locate` calls `classifyImport` [752:jl4-core/src/L4/Import/Resolution.hs:393], while its `ilBare` still looks the bare text up as a key [752:jl4-core/src/L4/API/VirtualFS.hs:164-170]; after #752 the browser's change site for step 2 is a new `ImportForm` arm in `locate`, and before it the strip goes into `apiModuleLookup` (10.6, Conditions) [read].
  _Names as built, unchanged._
  A slash-free simple or backticked name is bare: today's resolution, including the cut of a backticked dotted name (``IMPORT `a.b` `` is module `a`) and of a `.l4` suffix and the warning of §4.2(3).
  The path, root-relative and alias forms are as built (all backticked).
  _Qualified names (step 3 of 10.6, project-derived names only)._
  An unquoted dotted name whose last segment is exactly `l4` keeps today's meaning (`IMPORT foo.l4`).
  Any other unquoted dotted name is a **qualified name**.
  A segment that is not an identifier is quoted inside the name (the mixed form ``a.`b c` `` parses as a `QualifiedName`, p13).
  On today's binary a mixed form parses and is then cut at the last dot, so ``IMPORT l4.`actus-core` `` gives `I could not find a module with this name: l4` (exit 1, q1 of `review/probe.out`); a qualified name resolves only under R1 and R5.
  R1 changes both resolvers for step 3: the ladder's `writtenImportName`, and the pure resolver's `extractImportNames`, which today does not cut (10.5.1, Correction 3).
  The meaning of an unquoted dotted `IMPORT` changes at step 3 only, and the ruling that change needs (10.5.2) is not needed for step 2.
- **R2, a name that is not found.**
  After `l4:`, an unknown library name is an error that names the library spelling (``IMPORT `l4:<library>` ``) and lists the libraries the answering tiers hold.
  It does not fall back to a local file, and it does not print the bare-name ladder's list of five file locations, which is what today's binary prints for `l4:prelude` (P1) and is wrong for a reserved form.
  The list comes from the library tiers (the embedded map, or the `.l4` files of the pinned directory) and not from fixed text, because the set differs by release and by pin (20 of the 22 libraries in `l4-ide-build-100`, 10.5b "Released binaries").
  `` `l4:` `` with nothing after the colon (P3) gets a message of its own.
  A path import whose first segment is `l4` and which is not found (`l4/prelude`, the example in the request, 10.5b "Test of the claim") gets a hint that the library spelling is `l4:<library>` [proposed, not built].
  Where a project folder `l4/` holds the file, `l4/burden` resolves to the project's file with exit 0 and no message [measured, X3], so a user who meant the library gets a project file without a word, and no hint can fire there.
  For a qualified name (step 3), the error names the qualified name and also the old reading ("`a.b` is a qualified module name; to import module `a`, write `IMPORT a`"), and it does not fall back to the cut.
  Reason: with a fallback, a typo in `IMPORT Penal.Statute` would silently load a local `Penal.l4` (the dune and Haskell silent shadows of 10.2 point 3), and the meaning of a dotted import would depend on which files exist.
  The strictly behaviour-preserving variant, qualified lookup first and the old cut second, is available at that cost.
- **R3, a file and its own name (4a). Two forms; R3a is recommended.**
  _R3a, keep a self-import an error and make it readable (recommended)._
  A file whose `IMPORT` names itself stays an error, and the error names the import.
  `origin/main` has this rule since 2026-10-24: it prints "This IMPORT names the file it is in. A file cannot import itself." on the `IMPORT` line, and "This IMPORT makes a ring of imports: a.l4 -> b.l4 -> a.l4." for a ring (`selfImportDiags`, [M:jl4-lsp/src/LSP/L4/Rules.hs:931-937]; the errors page, [M:doc/reference/errors/README.md:416]; measured in 10.4b, "Trap 1 on `origin/main`").
  The code is in three commits that are on main and not on unstable: `f74116635`, which introduced `GetImportEdges` (the rule that `selfImportDiags` lives in) and `BlockingErrors.hs`, then `e089677b6` and `a1b6c3765` (`git merge-base --is-ancestor` exits 1 against `origin/unstable` for each) [measured, 10.4b].
  On unstable R3a is therefore a port and not a pick.
  `f74116635` is a VS Code feature of 11 files, so a port takes that feature or extracts the rule from it by hand.
  Applied alone, each of the three exits 1 with content conflicts, onto `origin/unstable` and onto #751 alike (10.4b names the files) [measured].
  There is also a conflict that no merge reports: main's edge rule cuts every `IMPORT` to its base name [M:Rules.hs:924-927], so carried verbatim onto #748 or #751 it would turn a path import of a same-basename file into a false self-import, and undo T1c-b of 10.4b [read, argued; not run].
  R3a on unstable therefore means main's rule re-based on `writtenImportName` and `classifyImport` [argued, not built].
  Whether to carry the commits by a merge of main or by taking them is not this survey's business.
  Where R3a sits in the order of work is open (10.6, "Order of work").
  On main the readable sentence is printed beside the GraphException and does not replace it (10.4b), so R3a adds a readable error beside the unreadable one and does not make the output quiet.
  Dropping the GraphException text is not part of R3a: main does not do it, and it would be a separate change.
  R3a changes no outcome: exit 1 stays, and `jl4/tests-cli/fixtures/selfimport/solo.l4` still fails [argued].
  The wrapper pattern (a `math.l4` that imports the library `math` and adds to it) is served by step 2: the wrapper writes ``IMPORT `l4:math` ``, and the reserved spelling reaches the library from beside any local file [argued, not built].
  _R3b, a self-import resolves to the library (the first draft's R3; the alternative)._
  The candidate whose URI is the importer's is dropped from the virtual-file tier (`vfsUris`, [W:Rules.hs:810], built from `relativePath` and `rootPath` at 800-805) and from the ladder's file candidates (`resolveLibrary`, [W:Rules.hs:476]), and resolution continues down the ladder.
  A few lines [argued].
  A `math.l4` containing `IMPORT math` then reaches the library `math` when no other copy is in scope [argued, not built].
  What it does next depends on names: if the file's own definitions do not repeat the library's, the library is imported and the file checks [argued, not built].
  Its costs:
  (i) it reverses main's rule, which says a file cannot import itself;
  (ii) it serves a pattern the corpus does not use: the one self-import in the corpus is a regression fixture named after no library (`jl4/tests-cli/fixtures/selfimport/solo.l4`, `IMPORT solo`), 1 of 1,443 files here, and commons has none (0 of 3,973) [measured, R-migration at `63254397f`];
  (iii) it moves the failure instead of removing it.
  Measured with three stand-ins (`wrap`, `wrapq`, `wrap2`), because R3b is not built and `IMPORT math` in a file not named `math.l4` reaches the library today (Stage 3 binary, `rev4/p/r3b`): a stand-in that defines `exp` at the library's type and uses `exp` itself exits 1 with "There are multiple definitions for the identifier exp", naming both; the same definition with no use of `exp` in the stand-in passes `l4 check` (exit 0, "Check succeeded."), and a file that imports the stand-in and uses `exp` exits 1 with the same error at its own use site; a stand-in that defines `exp` at another type (`STRING` to `STRING`) is accepted, exit 0 [measured];
  (iv) a case-variant `Math.l4` that holds `IMPORT math` still fails with the GraphException on the volume tested (HFS+): today's binary names `file://Math.l4` and `file://math.l4` in `[G]` (10.4b), and R3b compares the candidate's URI with the importer's, which differ in spelling [measured for today's behaviour, argued for R3b];
  (v) it relaxes a rule the code states, that one module name stays bound to one source across the whole build [W:Rules.hs:790-799]: with R3b the bare name `math` would name the local file for `main.l4` and the library for that file's own `IMPORT math`.
  That is tolerable only because the two have different keys, a file URI for the file and the embedded scheme (`jl4-embedded`, CLAUDE.md §5) for the library, which lives outside the `file:` scheme [W:Rules.hs:790-793], so neither module is mistaken for the other [argued]; the exception is limited to an importer asking for its own name.
  A genuine cycle through ``IMPORT `./math` `` keeps its `[G]` text under R3b unless the message is improved separately (measured on unstable, #748 and #751: it cannot tell the two apart); under R3a it gets main's text.
  Neither form reaches a cycle that passes through a library: a root `prelude.l4` that holds `IMPORT math`, where library `math` imports `prelude`, ends in `[G]` with exit 1 and no Warning line, the stack naming `jl4-embedded:/math.l4` and the root `prelude.l4` [measured, X4].
  The importer of the lookup that closes that cycle is the embedded `math`, whose URI is not the candidate's, so R3b drops no candidate; whether main's ring text names that cycle was not run.
  16 of the 22 libraries `IMPORT prelude` [measured, `grep` over `jl4-core/libraries` in [W]], so a root file named `prelude.l4` that imports any of them is in this case.
  Closing it needs the libraries' own imports to read the library tiers only, which ends the deliberate behaviour of [W:Rules.hs:795-799] and is a ruling (10.5b, the third rewrite hazard; 10.6, Conditions) [argued].
- **R4, local file and library (4b).** A shadowed library is announced as a warning diagnostic on the `IMPORT` line, in the language server and the editor, and the CLI keeps a stderr warning, whose form is (c) below [proposed, not built].
  Today the language server does not publish it: the shadow check reports through the server's logger, which writes to stderr (`makeDefaultStderrRecorder`, [W:jl4-lsp/app/Server.hs:65]; `logWith recorder Warning`, [W:Rules.hs:922]), and no code turns that log line into a diagnostic [read].
  A skeptic of the bench cards drove `jl4-lsp` with a local `math.l4` beside `main.l4` and saw the text on stderr and no diagnostic, and with `math.l4` also open nothing at all (the skeptic's own run, not repeated here); the as-built page says the warning goes "in the language server's log from the editor" [specs/as-built/import-resolution.md].
  So what R4 adds for the editor is a new diagnostic (10.7, item 33), in the pattern of `shortenedImportWarning`, which `GetImports` raises with `mkSimpleWarning` [W:Rules.hs:1617-1625] [read].
  It is more than a `mkSimpleWarning` in `GetImports` (10.7, item 55):
  (a) _The data is not returned._
  The resolver returns `ImportOutcome { importUri, vfsTried, libTried, embedTried }` [W:Rules.hs:598-611], with no list of copies and no winner.
  The shadow check runs inside the resolver (`warnOnLibraryShadow`, [W:Rules.hs:907-928]) and logs through the recorder.
  So R4 needs a wider `ImportOutcome` that carries the copies and the winner, or the check moved out of the resolver [proposed; argued from the code].
  (b) _The once-per-session dedup has to go._
  The check is "warned once per distinct configuration per session" through `shadowWarnedRef` [W:Rules.hs:917-919].
  A diagnostic that `GetImports` raises has to be raised on every run of the rule, for every importing file, or it disappears when the rule re-runs; so the diagnostic carries no per-session dedup [argued].
  (c) _The CLI's output changes._
  The CLI prints the diagnostics that the rules raise, because its Oneshot recorder renders the published diagnostics to stderr [W:jl4/app/L4/Cli/Common.hs:259-300] [read], and the `shortenedImportWarning` of the T2b rows (10.4b) is printed there.
  With the resolver's log line kept, the CLI would print the shadow twice, and `--json` would carry two entries [argued from the T2b row; not run].
  So the log line is either dropped where the diagnostic is raised, and the CLI then prints the warning once, as a diagnostic block in place of a log line, or both stay.
  The first is proposed [assumed, not ruled].
  "The CLI is unchanged" is therefore not true under either, and the pages and tests that quote the CLI's output are part of the change (10.6, step 1).
  (d) _A transitive shadow has no visible line to carry it._
  Library `math`'s own `IMPORT prelude` beside a local `prelude.l4` (X2) would raise its diagnostic on `jl4-embedded:/math.l4`, a file that nobody opens, so the editor says nothing for it, where the CLI's log line announces it today (10.4b) [argued].
  (e) _The virtual-file branch._
  A virtual-file hit returns before `resolveLibrary` runs [W:Rules.hs:827-835], so the editor with the sibling open needs the check on that branch as well, which means probing the library tiers on every virtual-file hit [argued].
  In the service every bundle file is registered as a virtual file [W:jl4-service/src/Backend/Jl4.hs:231-237], so a bundle's shadow takes that same branch.
  The service's failure path keeps only error-severity diagnostics [W:Jl4.hs:284], and a `git grep` of `jl4-service/src` finds no handling of a warning severity; whether any response there could carry a warning diagnostic was not traced, and (4b) stays unmet in the service response below [read].
  (f) _The text._
  The shadow warning's advice, to set `JL4_LIBRARY_PATH`, is not something an editor user can act on, and its rows carry absolute paths (`-> <abs>/math.l4`, 10.4b).
  As a published diagnostic it needs wording of its own: it advises `./math`, which chooses the local file with no warning (T2b), and, once step 2 exists, `` `l4:math` `` for the library, and it carries no absolute path, because a golden that captures one passes only on the machine that made it (CLAUDE.md §3.1.1) [argued; no golden was checked for a file that shadows a library].
  A quick fix that rewrites the line to either spelling is a candidate; it is not specified here, because the code-action handlers were not read.
  Among the CLI tests that assert the present text are [U:3093] ([W:3475]), which looks for ``Multiple differing copies of module `shadow-extra` ``; [U:3194, 3198] ([W:3576, 3580]), which look for ``Multiple differing copies of module `daydate` `` and `[chosen]   project root`; and [U:3205] ([W:3587]), which looks for ``Multiple differing copies of module `prelude` `` and for exactly two rows that begin with two spaces and `[chosen]` or `[shadowed]` [read].

### 10.5b Three ways to add new-style names on top of the fallback

All three sit on top of R1 to R5 of 10.5.3, and under the fallback none of them forces an edit to the existing corpus.
The options were named in the request; what follows is a working reading of each, proposed, not landed.

- **A, derived name, optional declaration.** A file's name is its path under the root of its project (the folder of the nearest `l4-project.json`, Stage 3 C2), `/` written `.`, `.l4` dropped; outside a project it is the bare file name.
  A file may begin with `MODULE <name>`; a name different from the derived one is a checked error that names both (Elm's rule [8]).
  A qualified import finds its file by turning the name back into a path.
- **B, declared name, authoritative.** A file that begins with `MODULE <name>` is known by that name whatever its path; a file without one by its derived name.
  A qualified import is found through an index: every `.l4` file under the root, read as far as its first declaration.
  Two files with one name are an error (PureScript's `DuplicateModule` [2]).
  A file that declares a name leaves the bare-name ladder, so a declared `prelude.l4` is not a candidate for `IMPORT prelude`.
  Against requirement (1) [argued]: this holds for every file that declares nothing, but it changes the target of a bare `IMPORT` in an importer that has not opted in, at the moment the file it used to reach adds a declaration.
  So B meets (1) only if "a file that does not opt in" is read as the file that is imported, and the author of a declaration owns the change for its importers; a variant that keeps (1) for importers leaves the declared file in the ladder under its bare file name as well, and then it no longer separates a local `prelude.l4` from the library at a bare import (the traps table below).
  The path decides only where the scan looks.
- **C, project name.** `l4-project.json` gains a `name` (Go's module path [3]; Catala's clerk has a `[project] name` "to refer to the project in multi-project setups" [12]); a file's identity is the project name plus its path under the root; no per-file keyword.
  The first segment of a qualified import is the project name.
  A root-level `prelude.l4` of a project named `acme` has the identity `acme.prelude` under C; only the bare-name ladder still reaches it, as `prelude`.

**Which option needs no edit, and what that gives up.**
All three need none: the fallback carries the corpus.
Two things that are easy to run together are kept apart here.
_Offering_ the reserved library spelling (``IMPORT `l4:prelude` ``) forces no edit: bare names keep working, and its price is a change to the shared classifier (a new constructor, tested before the guard that calls a slash-free name bare), a prefix strip in the library tiers of the ladder and in the pure resolver, and a ruling by Meng on the spelling.
_Rewriting_ the existing corpus to use it is the edit priced above (692 lines, 489 files, 196 or more goldens, and a commons pin bump), and is optional at any time after the spelling exists.
Making a `MODULE` header mandatory is a third and separate edit (every file, by hand).
Without the spelling the design gives up three things: a spelling for the library that no project file can equal, so the 22 bare names stay in one flat namespace where a project file wins and R4 only warns; a reserved prefix of the kind Go, Java, PureScript and Node have; and a self-describing name in each file.
With the spelling offered and no rewrite it gives up only the self-describing name in each file (step 4 of 10.6) and the protection of old files, which keep their bare names and so stay exposed to the shadow, where R4 warns in three runtimes and says nothing in the other three, and the libraries' own imports, which stay on the ladder (10.5.3 R3, closing paragraph).
What it keeps: every bundle, golden and released binary as it is.

**What each option cannot fix.**

- _A:_ the root-level `prelude.l4` against bare `prelude` (only R3b for a self-import, R4 by announcing it, or the reserved library spelling do); cross-project uniqueness; folder names that are OS-hostile; the first-path-segment escaping defect (the key stays a `file:` URI); names for the 3,945 non-identifier stems without quoting; the silent importer scan.
- _B:_ cross-project uniqueness (a duplicate is detected, not prevented); the first-path-segment defect; hermeticity of the embedded libraries (deliberate, see the comment and test cited in 10.4b); a declaration equal to a library's bare name unless it is refused; the language server's stale view of an unopened file; finding a module's file from its name without the index.
- _C:_ per-file control (a file cannot opt out); a single file with no manifest has no name; a bare `IMPORT` stays ambiguous, so neither trap; uniqueness of project names, which is convention only.
