# Relative Imports Specification

**Status (2026-10-26):** Stage 1 is **built**, in the draft PR into `unstable` that carries this edit (number filled in once it is opened); Stages 2 and 3 are **proposed, not landed**. Sections §0 and §1 describe the tree as it was on 2026-10-10 against l4-ide `539cad5fd` (merge of #605) and the installed `l4` of that date; where Stage 1 or #649 has since changed a fact, the list below says so and the section is left as it was written, because code and tests cite its numbers.

**What Stage 1 built** (the §4 design, as written): a backticked `IMPORT` name containing `/` is a path import, resolved against the importing file and never by the ladder; a leading `/` is refused; a bare name resolves as before, with the §4.2(3) warning. Core pure helpers (`classifyImport`, `pathImportFile`, `collapsePath`) are in `jl4-core/src/L4/Import/Resolution.hs`; the resolution is in `jl4-lsp/src/LSP/L4/Rules.hs` (`resolveRelativeImport`, `pathFailureMessage`), which serves the CLI, LSP, MLIR, REPL and service. Tests: `jl4-core/test/RelativeImportSpec.hs`, `jl4-lsp/test/RelativeImportSpec.hs`, `jl4-service/test/RelativeImportSpec.hs`, and the `l4 relative imports` group of `jl4/tests-cli/Main.hs` over `jl4/tests-cli/fixtures/relative-import/`.

**Where Stage 1 differs from this text, or found this text out of date** (each measured on 2026-10-26 against `unstable` `977691b36` plus this change):

- **§0 #3 and §8: the reduction was at three sites, not two.** `takeBaseName` of the written name was at `Rules.hs:958` (`unresolvedImports`, added by #649), `:1051` (`GetMixfixRegistry`) and `:1084` (`GetImports`). All three now call one function, `writtenImportName`: a bare name is still reduced, a path import is known by the text as written. The three must agree, or the service would report a resolved path import as unresolved.
- **§6, §8 and §9 Q1: `confined` already existed, as `LibraryScope`.** #649 (`main` 2026-10-15, reaching `unstable` 2026-10-18) added `AmbientLibraries | EmbeddedStdlibOnly` and the service already passes `EmbeddedStdlibOnly` at all four `oneshotL4Action…In bundleScope` sites (`jl4-service/src/Backend/Jl4.hs:158`). Stage 1 reads confinement off that scope (`confined = scope == EmbeddedStdlibOnly`) and adds no parallel flag. **Assumed, not ruled:** the derivation; no rule author can see it, and it reverts alone. The "service flag, about 40 lines" of §8 is therefore a comment on an existing type, and `jl4-service/src` is unchanged; the service gets tests only.
- **§9 Q1 is answered by #649, for bare names:** a deployment resolves its own files and the built-in stdlib, nothing from the host (`resolveLibrary EmbeddedStdlibOnly`, `Rules.hs:461`).
- **§4.5 messages, as built** (first lines pinned by `jl4-lsp/test/RelativeImportSpec.hs`): `I could not find a module at this path: <name>`; `This import leaves the root of this deployment: <name>`; `This import is relative, but <importer> has no directory to be relative to.`; and the §4.2(3) warning `IMPORT `<written>`resolved to module`<resolved>`; write `IMPORT <resolved>``. A leading `/` uses the "leaves the root" message in every runtime, as §4.2 rule 1 says; §4.5's "only a confined runtime emits it" holds for the climbing-out form only.
- **§4.2(3), where the warning is raised:** by `GetImports` only, and only for a bare import that resolved. `GetMixfixRegistry` asks about the same `IMPORT` and would say it twice. A bare import that does not resolve gets the existing not-found error, byte for byte, with the shortened name in it, as before.
- **§4.6: qualified names.** The claim that a module's definitions are reachable as `<module>.`name``did not reproduce: with `rates.l4` imported by path (one module, no `§` heading),``rates.`ratemark` ``is "I could not find a definition". Qualification here goes by section headings (see`doc/reference/libraries/README.md`, "When an imported name clashes"), so the open question of §9 Q5 does not arise for a module with no heading, and two same-named modules that define the same name clash as any two imports do ("multiple definitions"). Not checked: a module whose top heading equals its file name.
- **§8 core row, deferred to Stage 2:** `L4/API/VirtualFS.hs` keyed by path and the relative candidate in `moduleNameToCandidateUris` (the `TODO` stubs) are not in Stage 1. Nothing in the wasm path changes until Stage 2; a path import in a browser document does not work.
- **§8 docs row:** `doc/reference/libraries/IMPORT.md` does not exist on `unstable`; the `IMPORT` reference is the `## IMPORT` section of `doc/reference/libraries/README.md`. The pages changed are that section, `resolution.md` (a "Path imports" section), `doc/reference/errors/README.md` (four entries), `skills/writing-l4-rules/references/builtins.md` and `doc/courses/advanced/module-a4-production.md`, plus a checked example under `doc/reference/libraries/path-import-example/`. `doc/reference/libraries/README.md:41-48` and `doc/tutorials/getting-started/l4-cli.md` needed nothing more: #649 had already corrected the latter. The skill is duplicated in `legalese/l4-plugin` as a generated bundle (repo `CLAUDE.md` §1.0), which is now behind by this change until it is regenerated with `etc/build-plugin-bundle.mjs`.

**One-line summary.** `IMPORT` takes a bare module name and nothing else; a name that looks like a path is silently reduced to its basename (`takeBaseName`, `Rules.hs:935`), so `IMPORT \`../other-row/mod\``resolves to whatever`mod.l4`sits beside the importer, or to nothing, with no diagnostic that says so; this spec adds a path form that is reached only when the name contains a`/`, resolves importer-relative and nowhere else, keys the module by its normalised path so a diamond stays one module, and is confined to the bundle in the service and to the supplied files in wasm, leaving every bare-name import byte-for-byte as it resolves today.

## 2. The problem, against the five needs

| need                                                               | CLI, LSP, MLIR, REPL                                                                                                                                                                                                                     | service                                                            | wasm                 |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | -------------------- |
| (a) import a sibling directory's module by a relative path         | **no, and silently wrong**: the name is basenamed, so `../other-row/mod` means `mod` beside the importer or at the root (§0 #3, #4)                                                                                                      | no: `..` is refused at upload, and a path in the name is basenamed | no                   |
| (b) import from another subtree of one repository                  | only through `JL4_LIBRARY_PATH`, which is one directory and hides the stdlib (§0 #6); the two commons `cases/` rows are the live casualty (§0 #17)                                                                                       | no                                                                 | no                   |
| (c) the same source unchanged across runtimes                      | yes for one directory of bare names; nothing else works anywhere                                                                                                                                                                         | same                                                               | embedded stdlib only |
| (d) a symlink-free way to put two rows' modules under one importer | no; the symlink is the workaround (§0 #18)                                                                                                                                                                                               | n/a (a bundle is one tree)                                         | n/a                  |
| (e) path-canonical identity, one module per file however reached   | identity is the probed spelling (§0 #9); `..` is not collapsed by `normalise` (§0 #11), so a path form built naively would give `sub/../core.l4` and `core.l4` two identities; today no path form exists, so the question does not arise | same                                                               | by bare name         |

The premise holds: a relative path form is the right fix, because it is the only one of the options that lives in the source file and therefore travels with it to every runtime (need (c)); a manifest or a flag has to be shipped and interpreted separately in each of the four.

## 4. Recommended design

### 4.1 Grammar

No change to the parser.
The backticked name already admits every printable character but a backtick (§0 #1), so `IMPORT \`../other-row/mod\``lexes and parses today; the change is in what the resolver does with it.
The unquoted form stays as it is:`IMPORT sub/core`is a parse error today ("unexpected /",`exp3/slash.l4`tested) and stays one, because`/`is an operator token and because the path form should be visibly quoted.`AS` stays unsupported; it is a separate proposal.

### 4.2 Classification of the written name

Let `t` be the written name's text (`rawNameToText (rawName n)`, `Syntax.hs:94-97`).

1. If `t` contains `/`, it is a **path import**: `t` must be relative (not start with `/`); a leading `/` is reserved and refused with the "escapes the root" message until a root-relative form is specified.
2. Otherwise it is a **bare import**, resolved exactly as today, including the `takeBaseName` reduction, so `IMPORT foo.l4` and `IMPORT a.b` keep resolving `foo` and `a` (§0 #3; §5 row 5).
3. A bare import whose `t` differs from `takeBaseName t` (that is, it carries an extension or a dot) gets a new **warning**, "IMPORT `a.b` resolved to module `a`; write `IMPORT a`", so the silent reduction becomes visible without changing a result.
4. A path import is spelled with `/` only; `\` is not a separator on any platform (a backslash in a backticked name is an ordinary character today and stays one).

### 4.3 Resolution of a path import, as ordered steps

Given importer URI `u` and path text `t`:

1. If `u` has no directory, which is the case for an embedded library (`jl4-embedded:/`) and for a `project:/` document with no directory component, fail with the **no importing directory** message (§4.5).
   An embedded library never imports by path, so this arises only for a browser document.
2. Strip one trailing `.l4` from `t` if present; append `.l4`.
3. Join: `p = dir(u) </> t`.
4. **Collapse lexically**: apply `normalise`, then remove every `x/..` pair and every `.` segment by a lexical walk that does not consult the filesystem; if the walk would step above the start of a relative `p` (a leading `..` survives) or above the root of an absolute `p`, remember that it **escaped**.
   `normalise` alone is not enough (§0 #11).
5. If the runtime is **confined** (§6: the service and wasm are; the CLI, LSP, MLIR and REPL are not), an escaped `p` fails with the **escapes the root** message, and no probe is made.
6. Probe `p` in the VFS tier (`GetFileContents` of `roundTrippingFileUri p`), then, if the runtime is not confined, on the filesystem (`doesFileExist p`).
   No other tier is consulted: not `$JL4_LIBRARY_PATH`, not the project root, not the embedded stdlib, not XDG, not the bundle.
   A path import names one file, and the point of writing one is that no ladder decides it.
7. On a hit, the module's URI is `roundTrippingFileUri p`; on a miss, fail with the **not found** message listing the single location tried.

A bare import is untouched: steps 1 to 7 of today's `resolveImportShared` run exactly as they do (§0 #5).

### 4.4 Canonicalisation and module identity

The key of a path-imported module is the collapsed path of step 4, spelled relative when the importer's URI was relative and absolute when it was absolute, which is the regime `roundTrippingFileUri` already applies to bare names (§0 #9), so goldens that capture relative URIs do not move.
Two importers in the same session that reach one file produce one key: a bare import lands on `dir </> m.l4` normalised, a path import on the collapsed join, and for the same file in the same session both start from the same spelling of the directory, so the strings agree.
Where they could not agree is a file reached by a bare import through `$JL4_LIBRARY_PATH` (keyed under the env path) and by a path import (keyed under the importer-relative path): these are two modules in one session, by design, because the bare import chose the env copy and the path import chose the file, and the typechecker reports "multiple definitions" at the first use that cannot tell them apart, as it does today for any two same-named modules.
Symlinks are not dereferenced for identity, as today (§0 #9, #18).
The #573 invariant holds unchanged, because the rules stay keyed by URI and a path import contributes one URI per collapsed path; the #575 invariant is untouched, because the registry merge is not involved in resolution.

### 4.5 Error messages

All four are errors at the `IMPORT` line, in the style of the existing not-found diagnostic (`Rules.hs:958-967`), and the first line of each is stable text a test can match.

- **not found**: "I could not find a module at this path: `../other-row/mod` / Nothing it defines is in scope here; names you expected from it are reported as undefined. / Relative to `<importer>` that is `<collapsed path>`, which does not exist." The second line is kept verbatim from the bare-name message so readers recognise it.
- **escapes the root**: "This import leaves the root of this deployment: `../../x` / Relative to `<importer>` that would be `<collapsed path>`, which is outside `<root>`. / A relative import may reach any file inside the deployment and nothing outside it." Only a confined runtime emits it.
- **no importing directory**: "This import is relative, but `<importer uri>` has no directory to be relative to. / Write a bare module name, or supply the file through the editor's project files."
- **ambiguous**: cannot arise for a path import, which has one candidate; the bare-name shadow warning is unchanged.
- **cyclic**: unchanged; a cycle through a path import is caught where cycles are caught today (`GetMixfixRegistry` recursion, `Rules.hs:160-166`), and the message and exit code are the ones the `cycle2`, `cycle3` and `selfimport` fixtures pin.

### 4.6 Interactions

- `@lang`: none; the import name is not a localised word, and `@lang` is a per-file directive.
- `AS`: out of scope (§4.1).
- Qualified names: a module's definitions are already reachable as `<module>.\`name\``(tested in`ontology/exp1/right2.l4`, where the error listed `right.\`A victim\``and`core.\`A victim\``); the qualifier is the module's basename, so two path-imported modules with one basename in different directories yield one qualifier, and a use of it is reported as "multiple definitions" exactly as two same-named sibling modules are today.
  Giving a path-imported module a directory-bearing qualifier is left open (§9).
- The vintage axis (`RULES EFFECTIVE DATE`, `EVAL UNDER RULES EFFECTIVE AT`): none; imports are resolved before typechecking and do not read the clock.
- `@ref` annotations: `ResolveReferenceAnnotations` reads only `@ref-map` tokens today (`Rules.hs:1176-1186`, read); nothing to do.
- Exporters: Catala decides "library module" by basename against the embedded names (`Catala/Lower.hs:2367-2368`, read), so a path-imported module named `prelude.l4` in a subdirectory would be treated as the stdlib; this is a pre-existing basename assumption, noted in §9.

## 9. Open questions and what I did not check

1. **The service's bare-name fallthrough to the host filesystem.** `resolveLibrary` runs for a bare name that misses the VFS, with root = the first bundle file's directory relative to the service's cwd (`Rules.hs:732-734`, `Backend/Jl4.hs:191-196`); so a bundle that imports `foo` with no `foo.l4` uploaded would load `./foo.l4` from the service's cwd if one existed there.
   I read this; I did not run a service to confirm it, and the installed `jl4-service` binary is from March 2026 and would not have shown the tree's behaviour.
   The `confined` flag of §6 could also close this for bare names (VFS and embedded only), which is a separate decision because it changes an existing behaviour.
2. **Absolute zip entry names.** `isPathSafe` refuses a `..` component only (`ControlPlane.hs:623-624`); `saveBundle` writes `tmpDir </> "sources" </> relPath`, and `</>` discards its left operand for an absolute right operand (§0 #11, tested for `</>`).
   Whether the zip library ever yields an entry name with a leading `/`, and what the service then does, I did not check.
3. **The service's project root.** Taking the alphabetically first file's directory as root (§0 #7) means a bundle's root-tier imports depend on file naming; fixing the root to `./` is a small change outside this spec.
4. **The browser document's URI.** I did not find where the web IDE sets the Monaco model URI, so I do not know whether a websocket-mode document has a directory; the deployed server's root is `/app/libraries`, which makes the root tier of a browser import the stdlib directory.
5. **Qualifier for same-basename modules** (§4.6): whether a path-imported module should be qualifiable by more than its basename.
6. **`GetReverseDependencies`** lists the root and own directories only (§5 row 20); after path imports, find-references across directories would need the import graph rather than a directory listing.
7. **`Catala`'s basename test for library modules** (§5 row 21).
8. **Windows path spellings.** `roundTrippingFileUri` and the goldens are POSIX-shaped (`ImportDiagnosticSpec.hs` header); a path import on Windows collapses the same way lexically, but I did not test any Windows behaviour, and `l4-cli-test` is the only suite in the Windows CI job per that header.
9. **The `project:/` tier's origin.** `Rules.hs:681` calls it the Monaco VFS tier; no TypeScript in `ts-apps` or `ts-shared` produces a `project:` URI (grepped), so I could not confirm who sends them today.
10. **Whether any out-of-tree consumer parses the not-found message text.** The goldens do; `opm2l4` is mentioned in `VFS-IMPORT-NOISE-BUG.md` as filtering stderr; the new messages are additional lines, not changes to existing ones.
