# Name-resolution diagnostics: the EVENT type, and no cascades after a resolution failure (as built)

As built on `main` by the pull request that adds this page.
Source spec: none.
The change came from `unstable`: legalese/l4-ide#103 (`80217614cf`, issue smucclaw/l4-ide#915) and the first two of the three commits of legalese/l4-ide#152, `a4471aeb6` ("merge, don't overwrite, colliding builtin environment keys") and `daa7ee180` ("stop name-resolution failures cascading into bogus diagnostics", issue smucclaw/l4-ide#920).
The deploy gate of `jl4-service` (below) was added for `main`, and so were three changes made in the review of this pull request: the errors for an `@export` that takes an EVENT or a DEONTIC, the rule that the cascade filter drops a mismatch only for failures that its own module reported, and the rule that a name that did not resolve is not counted against its arguments.
This page describes only what `main` has.
Line numbers are in this PR's tree, merged with `main` at `b085e304d`.

Scope: the builtin scope in `jl4-core/src/L4/TypeCheck/Environment.hs`, the sentinel helpers and `getEntityInfo` in `jl4-core/src/L4/TypeCheck/Types.hs`, the error list and the type-mismatch rendering in `jl4-core/src/L4/TypeCheck.hs`, the validation of `@export` inputs in `jl4-core/src/L4/Export.hs`, and the deploy gate in `jl4-service/src/Compiler.hs`.
What L4 accepts changes in four ways.
`GIVEN e IS AN EVENT party action` now type-checks.
An `@export` rule whose input is, or holds, an EVENT or a DEONTIC is refused with an error of its own for each, because a request cannot carry either.
A type you declare yourself under the name `EVENT` with two parameters is now ambiguous with the built-in type, which could not be named before.
And the deploy gate of `jl4-service` now refuses a module that names a type nothing declares: it refused one before only because of the cascade that this change removes, and it accepted such a module when the undeclared type was a GIVEN input that the body did not use.
Everything else is which diagnostics are shown, and how a type mismatch reads.

## What it does

- `GIVEN e IS AN EVENT Party Act` resolves: the EVENT type is no longer hidden behind its own constructor.
- An `@export` rule whose input is, or holds, an EVENT is an error: `EVENT inputs are not supported for @export.`
  A request is JSON and JSON has no form for an event, so without this error the rule deployed with an input that no request could satisfy.
  `l4 check`, `l4 batch`, `jl4-schema` and the deploy of `jl4-service` all stop at it, as they stop at a function-typed input.
- An `@export` rule whose input is, or holds, a DEONTIC is an error too: `DEONTIC inputs are not supported for @export.`
  The same three lines follow the EVENT message's shape: the input is named, the reason is that a request has no JSON form for a DEONTIC, and the remedy is to take the plain facts the DEONTIC is made from as inputs and build the DEONTIC inside the rule.
  The built-in type is looked for by its unique, so `PROVISION`, its older spelling, is refused too, and a type of your own that is spelled `DEONTIC` and takes no parameters is not.
  An exported rule may give a DEONTIC as its answer; only an input is refused.
  The error is an ordinary checker error (source `check`, error severity), so the editors show it, `LSP.L4.BlockingErrors` counts it and the sidebar's Deploy button stays off, and `L4.API.l4Check`, which the web editor's WASM build answers with, reports it at severity 1.
- Both errors cover every input of an `@export` rule, however its type is known.
  A `GIVEN` with a written type is read from the source.
  A `GIVEN` with no written type takes the type that the checker worked out for the rule, with the substitution of the finished check applied: `` GIVEN `the duty` `` is refused when the rule hands it to a helper that takes a DEONTIC, or takes it apart with `CONSIDER … WHEN FULFILLED`.
  An input whose type stays open, or is a NUMBER or any other type that holds neither, is accepted.
  An `ASSUME` that the rule's own body reads is refused whether the module declares it or an imported module does, including one that the imported module itself imports, and whether or not it has a written type: an `ASSUME` named `the assumed duty` with nothing after the name is refused when the body takes it apart with `CONSIDER … WHEN FULFILLED` or hands it to a helper that takes a DEONTIC.
  A polymorphic `ASSUME` (`GIVEN a IS A TYPE`, `GIVETH AN a`, such as the prelude's `TBD`, in a file that has `IMPORT prelude`) has a declared type that holds neither type, so it is looked at for the type at each read of it in the body as well: a read that hands it to a helper that takes a DEONTIC or an EVENT, or takes it apart in a `CONSIDER`, is refused, and a read as a NUMBER is not.
  A read that is given arguments has the type of the call, not of the `ASSUME`, and is not looked at.
  A rule that has a definition, such as a DEONTIC written with `MEANS`, is not an `ASSUME`, and an exported rule may read it.
  An `ASSUME` that another rule of the module reads is refused as well, when an exported rule calls that rule, directly or through other rules of the module, and the read is at a type that holds an EVENT or a DEONTIC.
  The definitions under the `WHERE`s and `LET`s of each such rule are followed with it, and a rule that is handed on as a value, as to `map`, is followed as though it were called there.
  A call written with `'s` after its one input, as in `` n's `helper` ``, is followed as a call, and so is the read of a computed field of a record, which the checker turns into a rule whose one input is the record.
  The second line of the error then names the rule that reads the `ASSUME`, as in ``The input `the duty` is an ASSUME that `duty fulfilled` reads as a value whose type contains a DEONTIC, and this rule calls `duty fulfilled`, directly or through other rules. A request has no JSON form for a DEONTIC, so give `duty fulfilled` the DEONTIC as an input.``, and the EVENT message reads the same with `an EVENT` and `an event`.
  A polymorphic rule that reads a polymorphic `ASSUME` at one of its own type variables reads it at the type that each call gives that variable, so a call that gives the variable a type that holds a DEONTIC or an EVENT is refused, whether the rule stands under the exported rule's own `WHERE` or not, and a call that gives it a `NUMBER` is not.
  An `ASSUME` gets one error for one exported rule: the error without a reader when a read in the exported rule itself, its `WHERE`s and `LET`s included, is at such a type, and otherwise an error that names one of the rules that read it, the same one on every run.
  A rule of an imported module is not followed (see the limits).
- After a name that cannot be resolved (out of scope or ambiguous), the checker reports the resolution error, without the internal "should be reported as a bug" error and without the type mismatches that the unresolved name accounts for.
  Other diagnostics built on the unresolved name are still reported (see the limits).
- A type name that did not resolve is not checked for its number of arguments: a use of it gives the resolution error and no arity error.
- When two different types print the same (two `DECLARE Verdict`s), a type-mismatch message says where each was declared.
- `jl4-service` refuses a deploy whose module names an undeclared type, with that error.

  Each list is in the order in which the walk meets what it holds: an expression before the expressions inside it, and those in the order of the fields of the syntax tree that hold them.
  That is not always the order of the source: an event written with `AT` first holds its time in its last field, so the walk meets its time after its party and its action.

  The pass for the built-in types with no JSON form reads `inferredInputs`: every `GIVEN`, with the type from `inferredGivenTypes` for one that has none written, and every `ASSUME` that the body reads, found by its term kind in the entity table, with its declared type and then the type at each read of it in the body (`readTypes`), and every `ASSUME` that the body declares in a `WHERE` and reads (`localAssumes`), found in the body itself because the entity table holds only what the module and its imports declare, with the type that the checker recorded on the declaration and then the type at each read.
  `carriedUnsendable` reads the table and answers which of EVENT and DEONTIC it met first.
  `walkTopLevel` walks each top-level rule once, when the check first needs it, and keeps what `bodyReads` takes from the walk and the rules found in it (`rulesOf`): the rule and each definition under a `WHERE` or a `LET` of it, each with its type, the type variables that its type quantifies, those in scope, the calls in its own body, and the definitions directly under it.
  `reachedThroughCalls` starts from the reads of `ASSUME`s in the rules that the exported rules reach by calls, and passes each fact (a read at a type that holds an EVENT or a DEONTIC, or at a type that names a type variable in scope) back to each rule that calls the rule, or that it stands in, until no new fact arrives.
  A fact at a type variable of the rule crosses a call as the facts of the types that the call gives the variable (`callBindings`), from a one-way match (`matchTypes`) of the rule's declared type against the types that the checker recorded at the call, with synonyms expanded on either side up to `synonymExpansionFuel`.
  `typeNamesMet` lists the names that `carriedUnsendable` meets in a type, and both read it, so a type variable is looked for in exactly the places where an EVENT or a DEONTIC is found.
  The errors name the rule that reads the `ASSUME` in a field of their own (`ExportEventTypeInput` and `ExportDeonticTypeInput`), which holds no rule when that is the exported rule itself.
- `jl4-core/src/L4/Syntax.hs`: the term kind `AssumedTerm`, last among the kinds so that the encoding of the others is unchanged; `jl4-core/src/L4/TypeCheck.hs`: `scanFunSigAssume` (`:4186`) registers the term that an `ASSUME` declares with it, where a defined term has `Computable`; `jl4-lsp/src/LSP/L4/SemanticTokens.hs`: a reference to it is highlighted as a `Computable` one is.

## Behaviour and rules (read in code)

- **Builtin environment.** Two builtins that share a surface name keep both uniques, in table order, with no duplicates (`flip List.union`).
  The resolvers narrow the candidates: type resolution keeps only type candidates, term and constructor resolution only term candidates.
  EVENT is the only key that two entries of the table share: the table has 97 entries and 96 keys (counted at the time of writing), and the other keys that hold several uniques are the four comparison operators, which list them in one entry by design (measured by listing `initialEnvironment`'s keys that hold more than one unique).
- **Sentinels.** A failed resolution reports the real error and returns an `OutOfScope` sentinel whose unique is never registered in `EntityInfo`.
  `getEntityInfo` returns `Nothing` silently for a sentinel (`Types.hs:994`) and still reports `MissingEntityInfo` for any other miss (`Types.hs:996`).
- **Cascade suppression.** Drop each `TypeMismatch` that is the same on both sides once sentinels are treated as wildcards (`TypeCheck.hs:261`, `sameModuloOutOfScope`) and whose sentinels were all reported in this list.
  A sentinel carries the `Name` at which resolution failed, with its range and module, and the `OutOfScopeError`, `AmbiguousTermError` or `AmbiguousTypeError` that reported it carries the same `Name`; the filter collects those names from the list and looks each sentinel up (`TypeCheck.hs:250`).
  A sentinel that this module inherited through an import has the name from the other module, which the list does not hold, so a mismatch that mentions one is kept.
  A mismatch that differs somewhere else survives: NUMBER against `LIST OF <unresolved>` is kept, `LIST OF <unresolved>` against `LIST OF NUMBER` is dropped.
  Resolution failures themselves are never dropped, so a failing module still fails and still says why: `l4 check` still exits 1 on it, and the deploy gate refuses it.
  Filtering happens on the finished list, so resolution, pruning and overload selection are unchanged.
- **Same-name types.** If the two sides of a mismatch render identically, each side gets ` (<Name> defined at <file>:<range>, …)` for its user-defined type heads; predefined names (no range) and sentinels are skipped, and with nothing to say the plain rendering stays.
- **EVENT and DEONTIC inputs of an `@export`.**
  `carriedUnsendable` answers EVENT or DEONTIC for the built-in EVENT or DEONTIC type, for a type that has one of them among its arguments (`LIST OF EVENT …`, `MAYBE (DEONTIC …)`), for a synonym of such a type, and for a record or sum type with one of them in a field of one of its constructors.
  One input gets one error: the walk stops at the first of the two that it meets.
  It goes through the type arguments of a type, then what its synonym stands for, then the fields of the record, or of the constructors of the sum type, that it names; the fields of a record and the constructors of a sum type are taken in the order written, and all the fields of a constructor come ahead of the next constructor.
  The synonyms and the fields are read from the checker's entity table, so a type declared in an imported module is looked through too.
  A function type is not looked into, whether it is the input's own type, a type argument, or what a synonym stands for.
  The check for function-typed inputs is a separate pass, and it reads only the written types and the synonyms of this module: a function in a field of a record, or behind a synonym of an imported module, is refused by neither pass.
  The walk keeps one set of the types it has looked into for the whole input, so each type is looked into once at most, however many fields lead to it.
  A set kept for one path only, in a walk that also looked into the types that lead to neither builtin type, walked a chain of records that each have two fields of the next once per path: `l4 check` of such a file took 2.5 s at 24 records, 10.0 s at 26 and 42.2 s at 28, where the same file without `@export` takes 0.03 s, and with the one set all three take 0.03 s on this tree, as does such a chain whose last record refers back to a record that holds an EVENT in a field after the chain (measured).
  Which types lead to an EVENT or a DEONTIC is worked out once for the module, from the synonyms and the fields of the entity table (`leadsToUnsendable`): a type leads to one when what its synonym stands for, or the type of one of its fields, names an EVENT, a DEONTIC, or another type that leads to one, where the walk would meet that name, a name under a `FOR ALL` included.
  The walk does not look into a type that leads to neither, since it would find nothing there.
  The check asks about the type at each read of an `ASSUME`, so the reads of an `ASSUME` whose record holds neither builtin type do not each walk the fields of the record.
  Whether a type leads to one does not depend on the path by which the walk reached it, so skipping such a type changes no answer and not the order in which the rest is met.
  Working that out reads the synonyms and the fields of every type in the entity table, those of imported modules included, the first time the walk asks whether a type leads to one: for a type that is neither builtin type, once its type arguments hold neither, as for an input of type `NUMBER`.
  The fields of a type are gathered from its constructors in one pass, so the time that this takes grows with the number of constructors and not with its square.
  The EVENT and DEONTIC pass examines every `GIVEN` of an `@export` rule and every `ASSUME` that its body uses, the latter for its declared type and for the type at each read of it; the function-type pass examines the `GIVEN`s that have a written type and the `ASSUME`s of this module, and no others, so a `GIVEN` with no written type that the rule uses as a function, and an imported `ASSUME` of a function type, are not refused as function types.
  A `GIVEN` with no written type is matched to the argument of the rule's function type by its identifier and not by its position, because a type parameter (`GIVEN a IS A TYPE`) is not an argument of that type.
  The types of the entity table are read as the checker leaves them, so the substitution of the finished check is applied to the type of such an input first; without it the type is an inference variable and the input is accepted without a word.
  **The type at a read.** A name's own annotation holds the declared type of what it names (`resolveTerm'`, `Types.hs:894`), which for a polymorphic `ASSUME` is `forall a. a`.
  The instance that a read chooses is made by `instantiate` (`TypeCheck.hs:562`, called for a read at `:3198`) and is kept only on the annotation of the expression that reads it: `inferExpr` records the type it inferred there (`TypeCheck.hs:2426`), and `checkExpr` replaces it with the type the context expects (`TypeCheck.hs:2158`).
  So the annotation of a read that takes no arguments holds the type at that read, as an inference variable until the substitution of the finished check is applied, and the check reads it there.
  Measured on the reproductions, each with `IMPORT prelude`: `` `fulfilled` TBD `` and a rule that takes `TBD` apart in a `CONSIDER` are refused with `TBD` in the message, and `TBD + 1` is accepted; a polymorphic `ASSUME` of the module itself behaves the same.
  Without `IMPORT prelude` the name `TBD` is not in scope: `l4 check` fails on `` `fulfilled` TBD `` and on `TBD + 1` with "I could not find a definition for the identifier", which is a different error from the one of this check and is tolerated by the deploy gate as the name of an implicit input (measured below).
  The reads of an exported rule's own body, and of the rules of the module that it calls, are the ones looked at: a rule that is not exported, that the exported rule does not call, and that reads the same `ASSUME` as a DEONTIC, does not make an exported rule that reads it as a NUMBER refused.
  **An `ASSUME` that the body declares in a `WHERE`.**
  The entity table holds no local declaration, because a local declaration is in scope for the expression it belongs to and for nothing else.
  `bodyReads` finds the `ASSUME`s of every `WHERE` in the body (`localAssumes`), at any depth, the `WHERE` of a local definition included.
  The parser accepts an `ASSUME` among local declarations under `WHERE` and nowhere else: a `LET` holds definitions only, and `LET` with an `ASSUME` in it does not parse.
  The type of a declared `ASSUME` is on the annotation of its declaration (`scanFunSigAssume`, `TypeCheck.hs:4186`, which `scanFunSigLocalDecl` calls for a local one, as for a top-level one), an inference variable until the substitution is applied when no type is written; the types at the reads are those of `readTypes`, matched to the declaration by the identifier's unique.
  Only an `ASSUME` that the body reads is examined, a read anywhere in the body counting, its `WHERE` included, whether or not a local helper that makes the read is called (an `ASSUME` read only in a helper that is never called is refused, naming the `ASSUME`, as a top-level one is), and the two passes then treat it as they treat a top-level one: the first of its declared type and its read types that carries an EVENT or a DEONTIC gives its one error.
  A name in a `WHERE` does not hide a top-level one: the checker resolves a name by its type, so a local `ASSUME` that has the name of a top-level one is a different entity with a different unique, each read resolves to the one whose type fits, and the check goes by that one.
  The four ways to pair a top-level `shared` with a local `shared`, measured with `l4 check`: a top-level `NUMBER` and a local DEONTIC, read as a DEONTIC, is refused naming `shared`; the same pair read as a `NUMBER` is accepted; a top-level DEONTIC and a local `NUMBER`, read as a `NUMBER`, is accepted; the same pair read as a DEONTIC is refused naming `shared`, which is the top-level one.
  Two that both fit, a top-level and a local `NUMBER` or a top-level and a local DEONTIC of the one name, are not told apart: `l4 check` fails with "There are multiple definitions for the identifier", at the read.
  The checker is unchanged: the declarations are in the resolved body, and the types are on their annotations.
  No deploy-gate code was needed for either error: each is a checker error at error severity, and `blockingErrs` blocks every such error that is not an out-of-scope name.
- **Deploy gate.** `jl4-service` refuses a module that has an error at error severity, except an out-of-scope error for a name an expression reads, which becomes an implicit input of an `@export`.
  An undeclared type name raises the same error with the type `TYPE` (`TypeCheck.hs:1980`, the only place that does), and the gate now treats that one as blocking.
  Out-of-scope errors for terms carry an inference variable, not `TYPE`, and are still tolerated.
- **Stored deployments.** The loader of `jl4-service` compiles every stored deployment through the same gate, so a deployment whose exported rule takes a DEONTIC input, which an older service applied, comes up as `failed` when the service starts.
  The same holds for a rule whose input has no written type and is a DEONTIC or an EVENT by inference, and for a rule that reads an imported `ASSUME` of one of those types.
  The same holds for a rule that reads an `ASSUME` of one of those types that its own `WHERE` declares.
  Measured: a store written by a service built from the tree before that check, holding such a rule (a DEONTIC named `local duty`) and a rule that reads a local `ASSUME` of type `NUMBER`, answered HTTP 200 and `false` to the first and HTTP 422 with the message about an assumed term to the second; a service built from this tree over that store counted one failed and one ready in `/health`, answered `{"error":"Compilation failed","id":"duty","status":"failed"}` to `GET /deployments/duty` and HTTP 500 to its function list and its evaluation, logged the error with `local duty` in it, and answered the second as before.
  Measured: a store of three deployments, written by an older service (a `GIVEN` with no written type used as a DEONTIC, a `GIVEN` with no written type used as a NUMBER, and a rule that reads an imported DEONTIC `ASSUME`), answered HTTP 200 and `false` to the text `"FULFILLED"` for the first and to a request with no arguments for the third.
  A service built from this tree, started over that store, counted two under `failed` in `/health` (two failed, one ready, of three), answered `{"error":"Compilation failed","id":"duty","status":"failed"}` to `GET /deployments/duty` and the same for the third, answered HTTP 500 to their function lists and evaluations, logged the error with the three lines of the message for each, and answered the NUMBER deployment as before (`plus one` of `1` gives `2`).
  The files of the store are unchanged, except the ready deployment's `metadata-cache.json`, which the service rewrites.
  Measured: an older service built from the tree before this check applied such a rule over an empty store and answered `false` (HTTP 200) to the text `"FULFILLED"` for the input; a service built from this tree started over that store counted it under `failed` in `/health` (one failed, one ready, for a store of that rule and a plain one), answered `{"error":"Compilation failed","id":"duty","status":"failed"}` to `GET /deployments/duty`, answered HTTP 500 to an evaluation and to the function list, logged the error with the three lines of the message, and left every file of the store as it was except the plain deployment's `metadata-cache.json`, which it rewrote.

## Diagnostics

- New rendering, pinned by `not-ok/tc/tests/same-name-types-by-constructor.golden`: `Verdict (Verdict defined at same-name-types-by-constructor.l4:21:9-16)` against `Verdict (Verdict defined at same-name-types-by-constructor.l4:23:9-16)`, in the signature message and in the clause-input message.
- Removed from ordinary output: `The arities of the types do not match. I expected 0 arguments, but I found 2.` for a use of a type name that did not resolve, because kind 0 is the number `resolveType` makes up for a failure.
  On `main` it came with the resolution error whenever such a name was given arguments: a type of your own named like a built-in one (`DECLARE MAYBE a HAS …`, `DECLARE EVENT party action HAS …`), a parameterised type declared twice, and a type constructor that is not declared (`Duo OF NUMBER, NUMBER` with no `Duo`).
  A real arity mismatch, such as `MAYBE OF NUMBER, STRING`, is still reported.
- Removed from ordinary output: `I've encountered a resolved name that has no additional information stored for it: … This is an error in this system and should be reported as a bug.` for a sentinel (the text is at `TypeCheck.hs:4634`), and the matching "namely Verdict but is here of type Verdict" mismatches.
  The same lines also went from the output of the aliased-synonym case described in `tc-soundness.md`.

  Other work was running on the machine during both measurements, at a load average between 6.0 and 43.4 at their start and end.
  Measured the same way for following the calls, against the step before it and `main`, with nine runs each, `l4 check` CPU time is between 0.97 and 1.04 times that of the step before it, and between 0.93 and 1.03 times `main`, and the middle halves of the runs of the step before it and of this tree overlap on every file.
  The files are the 400 exported rules and the rule of about 6,000 terms above, each with and without `@export` and the `ASSUME`s; 400 exported rules that each call one helper that reads an `ASSUME` of type `NUMBER`, or one polymorphic helper that reads a polymorphic `ASSUME`, at a `NUMBER`; and 400 that each call, at a `NUMBER`, the first of a chain of 200 polymorphic rules that each hand their type variable on to the next, or the first of 1,000 that each call the next two; each with and without `@export`.
  The check follows those calls: the same chains with one more exported rule that hands what the first rule answers to a rule that takes a DEONTIC are refused, and the error names a rule at the end of the chain.
  The load average at the start and end of the runs is between 4.4 and 5.7.

  The CPU time is the median of three runs on 2,000 rules and one run on 5,000, at a load average of about 6, with a build running beside them.

## Limits and known defects (verified)

- Suppression covers `TypeMismatch` only (read in code, `TypeCheck.hs:261`), so other diagnostics built on a sentinel are still reported after the resolution error:
  `GIVEN x IS A Typo` then `x 1 2` also gives "You are trying to apply x of type Typo (which is not a function) to 2 arguments".
- The filter acts on a module's own error list, and drops a mismatch only when every sentinel in it was reported there.
  A module that imports one whose type failed to resolve did not report that failure, so it reports its mismatches against that type (`The first argument of function ... is expected to be of type Money but is here of type NUMBER`), whether or not it has unknown names of its own.
  The imported module's own check says the type is unknown, and the importer says what it makes of the poisoned type.
- The filter drops a mismatch only when every unresolved name in it was reported by the module being checked, so a module that has an undeclared type of its own and also imports a module whose type of the same spelling is undeclared keeps a mismatch between the two, and it reads as a vacuous one: they are two different unresolved names that print alike.
  Measured with `libmoney.l4`, which uses `Money` without declaring it (`GIVEN amount IS A Money`, `GIVETH A Money`, and a rule `` `total due` amount MEANS amount ``), and an importer `importer.l4` of three lines: `IMPORT libmoney`, `GIVETH A Money` and ``x MEANS `total due` 5``.
  `l4 check importer.l4` reports the importer's own `Money` as unknown (`2:10-2:15`), and also, at `3:9-3:22`, `The type of this definition must match its type signature at importer.l4:2:8-15, namely Money but is here of type Money`; the mismatch of the argument `5` against the imported rule, `is expected to be of type Money but is here of type NUMBER`, is reported as well, as the previous item says.
- An ambiguous type name can hide a real mismatch until the ambiguity is fixed: with two `DECLARE Verdict`, `GIVEN x IS A Verdict`, `GIVETH A NUMBER` and `f x MEANS x` give the ambiguity and nothing else, and the `Verdict`-versus-`NUMBER` mismatch appears once one declaration is removed.
  The filter never empties the error list of a failing module (read in code), and every golden in `jl4-test` is unchanged, so no file under `not-ok/` that failed to check passes now.
- An EVENT or a DEONTIC as the result of an `@export` is not an input and is not examined: an EVENT evaluates and is returned as `{"EVENT": [party, action, time]}`, and at `/evaluation` a DEONTIC, written `DEONTIC` or `PROVISION`, is answered by running it against the `startTime` and `events` of the request (`doc/reference/regulative/deontic-export-example.l4`: `the duty` answers `FULFILLED`, measured on a service built from this tree).
  `/evaluation/batch` and MCP `tools/call` do not run such a rule: they answer with the duty unrun, `{"OBLIGATION": {...}}`, which no `returnSchema` describes, and a `startTime` and `events` sent with the request change nothing, although MCP `tools/list` marks them required.
  Measured on a service built from this tree, with that file's `the duty`, a rule written `GIVETH A DEONTIC`, one written `GIVETH A PROVISION` and one with no `GIVETH`: `/evaluation/batch` and MCP `tools/call` give the `OBLIGATION` with and without a `startTime` and `events`, at MCP in the shape of input that `tools/list` gives for each rule.
  Read in code: the batch handler in `jl4-service/src/DataPlane.hs` evaluates every case as a value, `buildArgPairs` in `jl4-service/src/McpServer.hs` does not pass on a `startTime` or `events` sent beside the rule's inputs, and `runMcpEvaluation` evaluates the rule as a value.
- The `returnSchema` of an `@export` that gives back an EVENT describes that object: one required key, `EVENT`, holding an array whose `prefixItems` are the schema of the party's type, the schema of the action's type and a number, with `minItems` and `maxItems` of 3.
  `L4.FunctionSchema.typeToParameter` builds it, so an EVENT in a LIST, in a MAYBE, in a field of a record and behind a synonym is described the same way, and jl4-service and the editor's export summary both take the return schema from `L4.FunctionSchema.returnSchemaOf`, which gives none for an answer written `DEONTIC` or `PROVISION`.
  Pinned by `FunctionSchemaSpec` (jl4-core-test), `InspectorReturnSchemaSpec` (jl4-lsp-test), and the block "the returnSchema of an @export that gives back an EVENT" in jl4-service-test, which checks the answers of `/evaluation`, `/evaluation/batch` and MCP `tools/call` against the schema the same deployment publishes.
  `FunctionSchemaSpec` also pins that a record of two type arguments is described by its own fields and not as an event, and jl4-service-test's "publishes no returnSchema for a rule whose answer is written DEONTIC or PROVISION" pins that the service gives none for either spelling.
  `returnSchemaOf` and the service's `isDeonticType` match the type as it is written and do not expand a synonym.
  So a rule whose answer type is declared as a synonym of `DEONTIC`, `DECLARE Duty IS DEONTIC Person Action` with `GIVETH A Duty`, is published and answered as a value; measured on a service built from this tree, its `isDeontic` is false, its `returnSchema` is `{"type": "object"}`, its inputs do not include `startTime` or `events`, and its answer is the duty itself, `{"OBLIGATION": {...}}`.
  The party and the action are described by the schemas of their types, and those do not describe every answer of their types.
  Measured with Ajv's JSON Schema 2020-12 validator, on a service built from this tree, at `/evaluation`, `/evaluation/batch` and MCP `tools/call`: the schema rejects an event whose party is the record `Party`, whose one field `name` is a `STRING`, `{"EVENT": [{"Party": {"name": "Alice"}}, "delivery", 3]}`, or a `MAYBE` that is `NOTHING`, `{"EVENT": [null, "delivery", 7]}`, the two shapes of smucclaw/l4-ide#1010.
  It accepts an event whose party is the record `Loose`, whose one field `nickname` is a `MAYBE STRING`, `{"EVENT": [{"Loose": {"nickname": "Al"}}, "delivery", 3]}`, because the schema of a record requires only the fields that are not a `MAYBE`.
  It rejects an event whose action is a constructor that holds fields, `{"EVENT": ["Buyer", {"pay": {"amount": 100}}, 4]}`, or a constructor named `false`, `{"EVENT": ["Buyer", false, 2]}`, and it rejects those two actions given back on their own, `{"pay": {"amount": 100}}` and `false`, because the schema of an enum is a string with the enum's names.
  An event made by `WAITUNTIL 5` is answered `{"EVENT": ["NEVERMATCHESPARTY", "NEVERMATCHESACT", 5]}`, whatever the types of its party and its action.
  For an `EVENT Person Action`, where `Person` is the enum `ONE OF Seller, Buyer` and `Action` the enum `ONE OF delivery, payment`, the schema rejects it, alone and as an item of a `LIST OF EVENT`, because the schema of an enum lists only the enum's own names.
  For an `EVENT STRING STRING`, and for an `EVENT Who Who` where `Who` is declared as a synonym of `STRING`, it accepts it, alone and as an item of a `LIST OF EVENT`.
- The function-type check looks only at the written types and the `ASSUME`s of this module that have a type written after `IS A`, so these pass it: a `GIVEN` with no written type that the rule uses as a function, an imported `ASSUME` of a function type that the rule calls, a function `ASSUME` written with its signature before it, a function in a field of a record, and a synonym of a function type that an imported module declares.
  Measured, `l4 check` accepts each: a rule with `GIVEN p` whose body is `p OF TRUE`; a rule whose body is `` `imported function` OF 1 ``, where an imported file declares ``ASSUME `imported function` IS A FUNCTION FROM NUMBER TO NUMBER``; a rule whose body is `bump 2`, where the module has `GIVEN n IS A NUMBER`, `GIVETH A NUMBER` and `ASSUME bump`; a rule that takes a record with a field of type `FUNCTION FROM NUMBER TO DEONTIC Person Action`; and a rule that takes an input of the type `Maker`, where an imported file declares `DECLARE Maker IS A FUNCTION FROM NUMBER TO DEONTIC Person Action`.
  Measured on a service built from this tree, the first three deploy and every request to them answers HTTP 422, so none of them fails quietly.
  The rule with `GIVEN f` and the body `f 3 + 1` is listed by the function endpoint (`GET /deployments/<id>/functions/<fn>`) with `f` as a required input of type `object`; a request without `f` answers `Parameter 'f': missing required parameter`, and a request that sends `f` answers `Internal error:` with `expected a function but found: 3` and `Please report this as a bug.`
  The rules that call an imported function `ASSUME` (to a NUMBER, or to a DEONTIC that a helper takes) and the one that calls `bump` answer that the service `needed to know the value of` the name `but it is an assumed term`.
- A polymorphic `ASSUME` is not refused as such, only when a read of it in an exported body, or in a rule that an exported rule calls, has a type that holds a DEONTIC or an EVENT.
  Measured on a service built from this tree, a rule that reads one as a NUMBER deploys, and every request answers HTTP 422, whether or not a value is sent for it.
  With a polymorphic `ASSUME` of the module itself plus 1, the function endpoint (`GET /deployments/<id>/functions/<fn>`) lists it as a required input of type `object`, as `poly number`, and the message says that the service `needed to know the value of` the name, `but it is an assumed term`.
  With `TBD + 1` the answer depends on whether the file has `IMPORT prelude`.
  With it, the function endpoint lists no input, since `TBD` is the prelude's, and the message is the one about an assumed term.
  Without it, `TBD` is an unknown name and `l4 check` fails, and the service deploys the rule all the same, because the deploy gate tolerates an out-of-scope name that an expression reads: the function endpoint lists `TBD` as a required input of type `number`, and every request answers `Internal error:` with `TBD` `is not in scope.` and `Please report this as a bug.`, with or without a value sent.
  The same holds for `` `fulfilled` TBD ``, where the unknown name is listed as a required input of type `object`: `l4 check` fails, and the service deploys the rule and answers every request with that message.
  The same endpoint lists an `ASSUME` of the module with no written type, and one written with its signature before it, as a required input of type `object`, and the value sent is ignored in the same way.
  The endpoint at `GET /deployments/<id>` has an empty list of properties for each of the rules of these measurements, including one that reads an `ASSUME` of type `NUMBER` with a written type, which the function endpoint lists as a required input of type `number`, so the metadata endpoint says nothing about any of them.
- An `ASSUME` that the body declares in a `WHERE` is refused when the body reads it as an EVENT or a DEONTIC and in no other case.
  A function `ASSUME` that the body calls, and a `NUMBER` `ASSUME` that the body reads (`` `r` MEANS `local n` + 1 `` with ``ASSUME `local n` IS A NUMBER`` under its `WHERE`), pass `l4 check` and deploy.
  Measured on a service built from this tree, the function endpoint lists no input for either, and every request answers HTTP 422 with the message that the service `needed to know the value of` the name, `but it is an assumed term`, whether or not a value is sent for it.
- The EVENT and DEONTIC checks follow the rules of the module that an exported rule calls, and not a rule of an imported module: the checker's view of an import holds the types of its rules and not their bodies (`unionImportedCheckEnv`, `Types.hs`), and `validateExportInputs` reads the module being checked.
  Measured with `l4 check`: a file `lib3.l4` that declares ``ASSUME `the lib duty` IS A DEONTIC Person Action`` and a rule `` `lib duty fulfilled` `` that reads it in a `CONSIDER`, and a file that has `IMPORT lib3` and an `@export` rule whose body is `` `lib duty fulfilled` ``, passes.
  `doc/reference/regulative/DEONTIC.md` states it under "What the check does not catch".
- The function-type check does not follow a rule that the exported rule calls: with `ASSUME bump IS A FUNCTION FROM NUMBER TO NUMBER`, a rule `` `bumped` MEANS bump 1 `` and an `@export` rule whose body is `` `bumped` ``, `l4 check` passes (measured), where an `@export` rule that reads `bump` itself is refused.
- A read in a definition under a rule that the exported rule calls counts whether or not the rule calls that definition, as a read under the exported rule's own `WHERE` does: a helper whose body is `1` and whose `WHERE` defines an `unused` that reads an `ASSUME` of type DEONTIC makes the `@export` rule that calls the helper refused, though no evaluation reads the `ASSUME`.
- A polymorphic rule is followed by what each call gives its type variables, from a match of its declared type against the types at the call; where the match gives a variable no type, because the synonyms on the two sides run deeper than `synonymExpansionFuel` or a type there is still open, a read at the variable is accepted, as an input whose type is still open is.
  The error names one rule that reads the `ASSUME`, and not the calls that lead from the exported rule to it.
- An input whose type has an EVENT or a DEONTIC only as a type argument that the type never uses is refused too: with `DECLARE Phantom a HAS n IS A NUMBER`, `GIVEN p IS A Phantom (EVENT Person Action)` gives `EVENT inputs are not supported for @export.`, and `GIVEN p IS A Phantom (DEONTIC Person Action)` gives `DEONTIC inputs are not supported for @export.`, though a value of that type holds neither.
- A type of your own named `EVENT` with two parameters is ambiguous with the built-in one, as a `DECLARE MAYBE a` is with `MAYBE`; before, it checked, because the built-in type could not be named (`not-ok/tc/user-declared-event.l4`).
  A declaration of `EVENT` with no parameters is not affected: the number of parameters rules the built-in type out (measured on a one-field record).
- No test pins the time of the walk of the body (`bodyReads`): a walk that reads a body more than once, or whose time grows with the depth of the body, passes every test.
  The measurement above is the only evidence for it, and it is taken by hand.
  The rules that an exported rule calls are walked by the same walk; the watchdog of the examples of rules that call each other, and of sixty levels of rules that each call the next one twice, pins that following the calls finishes, and not how long it takes.
  Two examples pin the time of the input check, each in one case only: many reads of an `ASSUME` of a record that holds neither builtin type, and a sum type of many constructors in a module whose one exported rule takes a `NUMBER`.
  Two examples pin how what following the calls allocates grows, each in one shape: a chain of polymorphic rules that each read a polymorphic `ASSUME` at their own type variable and call the next one, and a chain of rules that each read an `ASSUME` of type DEONTIC and call the next one.
- `sameModuloOutOfScope` compares `Forall` bodies without alpha-renaming, so two foralls equal up to renaming compare unequal and the mismatch is kept, the conservative direction (read in code, `Types.hs:768`).
- Measured: a name that cannot be resolved as a term (`f MEANS undefinedname`) is reported once both with and without this change, so the cascade came from unresolved type names.
- `extractImplicitAssumeParams` (`jl4-core/src/L4/Export.hs`) still reports an undeclared type name as an implicit input of the type `TYPE`; the deploy no longer reaches it, and `parametersFromDecideWithErrors` (`jl4-core/src/L4/FunctionSchema.hs`) is unchanged and still calls it.
- The editor's completion list offers `EVENT` twice, once as a type and once as a constructor, as it offers a user's record type (measured on a record `Person`); before, only the constructor.
- Every type-mismatch message that prints both types goes through `prettyMismatchedTypes`; the `AS STRING` argument message prints only the given type and is not changed.
