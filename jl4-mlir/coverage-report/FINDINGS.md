# Compile-coverage triage findings

Generated by `scripts/coverage-sweep.py` over **432 `.l4` files** in the repo
(`jl4-mlir wasm --mlir-only`: typecheck + lower + schema, no LLVM toolchain).

> **Refreshed on the `mlir-review` branch.** The composition of the
> `has-unsupported` set has _completely turned over_ since the original M2 sweep
> (see "M2 → now" below) — the count is still 2 files, but for entirely
> different reasons. The end-to-end `.l4 → wasm` path is now also verified
> locally (see "Differential parity").

## Outcomes

| Outcome           | Count | Meaning                                                             |
| ----------------- | ----: | ------------------------------------------------------------------- |
| `clean`           |    36 | all `@export`-ed functions lowered, every one `supported: true`     |
| `has-unsupported` |     2 | compiled, but ≥1 export flagged `supported: false` (fail-loud)      |
| `no-exports`      |   342 | typechecks but has no `@export` (course material, tests, fragments) |
| `typecheck-fail`  |    51 | jl4-core rejected it (a language/parse issue, not a backend gap)    |
| `lower-fail`      |     1 | misclassified — a deliberately-broken parse fixture (see below)     |

## The `has-unsupported` set (2 files, 2 functions)

| File                                                 | Function        | Reason                                                                          |
| ---------------------------------------------------- | --------------- | ------------------------------------------------------------------------------- |
| `jl4/examples/ok/mixfix-garden-path.l4`              | `tax-on`        | ad-hoc overload collision: multiple `tax_on` at arity 3 share one WASM symbol   |
| `jl4/experiments/thailand-cosmetics/orchestrator.l4` | `evaluateClaim` | CONSIDER pattern constructors `LEFT`/`RIGHT` could not be resolved to enum tags |

Both are **honest refusals** (`supported: false`), routed to the fallback
evaluator rather than silently mis-compiled — and both are _new since M2_,
surfaced by the adversarial-review fail-loud work (QW1: same-arity overload
detection + unresolved-enum-tag guarding). Before that work, the overload
collision picked an arbitrary body and the unresolved CONSIDER arms lowered to
a constant-true match — i.e. silent wrong answers.

## M2 → now: what changed, and why

The original M2 sweep reported **2 `has-unsupported`** hits, both the same
`Eligible-Service-Requirement` **deontic REGULATIVE** rule in the two copies of
`ceo-performance-award.l4`. That is no longer the picture:

1. **M6 deontic support landed.** `ceo-performance-award.l4` is now **`clean`** —
   the REGULATIVE construct is handled (JS-runtime-over-schema-tree), so it is no
   longer refused at lowering.
2. **Fail-loud surfaced two real silent-degradation cases** (QW1, this review):
   the `mixfix-garden-path` overload collision and the `thailand` CONSIDER enum
   gaps are now correctly flagged instead of silently returning wrong answers.

Net: the `has-unsupported` _count_ is unchanged (2), but the _composition_ fully
turned over — coverage genuinely improved (deontic gained; silent mis-compiles
converted to honest refusals).

## The `typecheck-fail` / `lower-fail` numbers are not backend gaps

- The single `lower-fail` (`jl4/examples/not-ok/tc/scombinator-fragment.l4`) is a
  deliberately-broken indentation/parse fixture the classifier didn't bucket as a
  typecheck failure. There are **no genuine backend crashes** on the corpus.
- The 51 `typecheck-fail` files are dominated by `experiments/` (WIP/scratch) and
  `not-ok/` + CLI garbage fixtures designed to fail; they are rejected by
  jl4-core at parse/typecheck and never reach lowering — a _language coverage_
  surface, not an MLIR-backend surface.

## Support / refuse decisions

- **Deontic / REGULATIVE:** now **supported** (M6, JS-runtime-over-schema-tree).
  The M2 "refuse deontic" decision is superseded.
- **Ad-hoc overload at the same arity:** refuse (WASM symbols collide); flagged
  `supported: false`. Disambiguation would need name-mangling by signature.
- **Unresolved CONSIDER enum constructors:** refuse; lowering cannot map the arm
  to a tag. (Resolves once the enum is in scope / imported.)
- **Lambda / higher-order, IO (FETCH/POST/ENV):** refuse; no exported instances
  in the corpus, so latent.
- **Everything else that typechecks + exports:** supported (36 files lower
  cleanly; 2 correctly refused).

## Differential parity (end-to-end, verified locally)

`scripts/parity-harness.mjs` was run on the `mlir-review` branch with the full
LLVM 22.1.7 toolchain (Homebrew `llvm` + `lld`) against a live jl4-service over
the 4-fixture corpus (`test.l4` + 3 deontic fixtures): **20/20 byte-identical,
`PARITY OK`, exit 0** — zero `differs`, zero `wasm-error`. The trace=full
sub-matrix is the known M5-slice-1 backlog (12 byte-identical / 8 trace-differs,
non-gating). This is the first end-to-end (`.l4 → MLIR → wasm` vs reference)
confirmation from repo state; the hardened gate (`scripts/parity-gate.mjs`) is
wired into CI (`pr-checks.yml`).
